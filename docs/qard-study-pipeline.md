### One daily loop

1. Open **Today** and complete due card reviews and due objective checks from subjects already studied. New course setup adds no due dates. If a review backlog consumes the session, defer new material.
2. Open **Learn → Programming**, choose the earliest ready objective in the active unit, and use its **Teach** action. Read the linked source, predict an example and explain the mechanism from memory. Lessons may span days. Existing familiar material can be tested diagnostically rather than reread repeatedly; a source note marked Done is not automatically a mastered Qard objective.
3. After studying, use the owning note's **Study this note → New cards → Normal session**, within the existing global five-new-card allowance. Ordinary ratings also contribute to the matching first-pass plan. If no cards exist, use explanation/application recall; adding cards later is a separate authoring task. Do not run the plan's automatic introduction queue as an additional daily quota.
4. After three to five related objectives, revisit an explanation or application problem and use each objective's Learn check when appropriate. Saved practice tests have been removed for now; the current route uses Learn and cards.
5. On later days, let Today bring back the checks and cards due from actual study. A lesson alone does not establish mastery. Qard uses a 70% assessment pass boundary and promotes an objective to mastered after passing evidence on two days at least two days apart, with harder application work after the first pass; confidence and weak answers can keep it shaky or return it to teaching.

### When to advance

Keep the scheduler's 90% target. It controls review timing; it is not a percentage-complete goal. Raising it does not establish that unseen cards are known. Deck recall statistics accumulate ratings and count Hard as remembered, so they are different from a fresh first-attempt checkpoint.

Use this proposed manual checkpoint instead:

1. Complete first-pass coverage of the Programming deck. Coverage counts exposure, including Again; it is only the first condition.
2. At least two days after the final new introduction, choose Programming, **All cards → Shuffle → Cram**. Give each answer before revealing, count only the first attempt and tally correct answers yourself. Count skips, unseen answers and missing essential points as unsuccessful.
3. For the present 102-card scope, a 90% checkpoint requires at least **92 correct**. Use `ceil(0.90 × current active card count)` if the deck grows. This is a proposed readiness policy, not a validated measurement of long-term retention. Cram does not store a score or alter FSRS schedules.
4. Also explain or solve one applied problem from each major block: language/type fundamentals, runtime/memory, concurrency/async, and the web pipeline. Fact-card accuracy alone does not establish engineering judgment.
5. If the checkpoint is weak, keep Programming active, repair its weak cards, follow due reviews and check again after a delay. Once it passes, start the next area while continuing scheduled Programming maintenance. Qard does not automatically unlock an area or mark this checkpoint passed.

New plan queues stop after 19 November. If the first pass is unfinished, edit the plan's date; if coverage is complete but the checkpoint needs work, continue via Programming's Today reviews. Deleting the plan does not delete cards or history. The approved fresh start removed the experimental ratings; no further reset is needed when moving to another subject.

## Daily session

Budget roughly 30–45 minutes initially. Timings are a suggested routine, not application quotas.

During lesson-led Programming study, use Learn to choose the next concept and the source note's New cards session for introductions. The native plan records coverage from those ratings too. Its automatically selected queue is an alternative coverage route; do not run both introduction routes merely to fill quotas.

1. **Review, 10–15 minutes.** Run **Qard: Open today**. Complete due objective checks if using Learn, then existing-card reviews across every previously introduced area. A 15-card batch is one sitting, not a daily maximum. Continue if manageable; when a backlog grows, give review the available time and defer new introductions.
2. **Learn, 15–20 minutes.** Choose the next ready objective in the active Qard Learn course. Use `Vault/Home/Topics.base` and its **Learn next** view for additional source browsing or readiness review. Pick one concept from the active study area. Read its operating idea and important boundary, inspect an example, then close the note and explain the mechanism from memory. Finish with one prediction, tradeoff, debugging question or small implementation exercise. A large topic can span several days; do not force one completed note per day.
3. **Retain, up to five new cards.** If that concept has Qard cards, run **Qard: Study this note**, choose **New cards**, and use a **Normal session**. Keep introducing cards from the same concept on later days until its useful new cards are introduced, then advance. Do not introduce unrelated cards from all decks just to fill the allowance. Five is a global daily allowance, not five per topic.
4. **Repair, a few minutes.** Flag ambiguous/oversized cards with **Needs fixing**. Repair the most useful one after study; split only genuinely independent targets. Rate forgotten essential answers Again rather than Hard.

If a concept has no cards, recall its explanation and solve the application exercise anyway. Add cards only for useful durable targets in the existing owning note through the normal authoring/review workflow; lack of cards must not exclude a topic. Qard can offer **Teach me this note** when AI is configured, but teaching is optional and no provider call is required for this routine.

Finish the day when due work and the selected learning block are complete. Do not repeatedly reopen All merely to make the queue nonempty. Use Cram for an optional extra rehearsal without recording normal ratings.

## Weekly check and interview practice

Practice tests are deferred for now. Use Learn objective checks and source-note application problems for the current routine. If practice tests are reintroduced later, the following prompt is available as an optional starting point.

Suggested prompt:

> Build a ten-question technical interview test from these notes. Include two mechanism questions, three explanation or tradeoff questions, three debugging or prediction questions, and two application/design scenarios. Prefer short and long written answers. Test unfamiliar examples, assumptions, important limits and justification. Identify missing source evidence instead of inventing facts. Avoid paraphrasing the existing flashcards.

Inspect missing rubric points, Try again before Model answer, then compare and Ask or Dispute when needed. Repair existing cards before creating duplicates. A test assesses code as text; run important code separately. A voice answer during card study is temporary playback, not transcription or AI grading.

The current Programming plan uses a provisional coverage date because native Qard plans require a date. When an interview has a real date, add or adapt a plan for its relevant scope. Plan coverage counts exposure, including Again ratings; use fresh application answers to assess understanding. No scheduled AI or publication jobs are activated by this setup.
