<p dir="auto">Classic ML fits a well-defined prediction problem with representative labeled data, such as classification, regression, or ranking. <em><a href="Home/AI &amp; ML/AI &amp; ML.md" class="internal-link">AI &amp; ML</a></em></p>
</div></div></blockquote></span><h2 id="ai-ml-llm">LLM</h2><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">How do Matryoshka embeddings reduce vector storage, and how should the smaller size be validated?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Matryoshka training makes shorter prefixes of the full vector useful on their own, so a model with a <code>dimensions</code> option can return 256 or 512 values instead of the full size. Indexing 256 rather than 1536 float values cuts raw ANN vector storage by about six times and also reduces similarity work. Recall is not guaranteed, so the same labeled queries must be compared at several dimensions using Recall@k and latency. If full vectors are used for reranking, retaining or recomputing them adds storage, API cost, or latency outside the smaller index.<br />
<em><a href="Home/AI &amp; ML/LLM/Embeddings.md" class="internal-link">Embeddings</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">Why can switching to a higher-scoring embedding model cause recall to drop on existing queries?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Each model defines its own vector space. Comparing a query from the new model with stored vectors from the old one produces meaningless distances and broken rankings. Build the new corpus index before switching query traffic, and include the model name and version in embedding-cache keys.<br />
<em><a href="Home/AI &amp; ML/LLM/Embeddings.md" class="internal-link">Embeddings</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">Why is adjusting temperature and top_p simultaneously discouraged?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Both reshape the token distribution through different mechanisms. Temperature sharpens or flattens logits, while top_p truncates candidates at a cumulative-mass threshold. Changing both makes an observed output shift harder to attribute. Tuning one and leaving the other at its default keeps evaluation legible.<br />
<em><a href="Home/AI &amp; ML/LLM/Generation.md" class="internal-link">Generation</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">Why can a grounded response still contain unsupported claims despite citation tags?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Citation markers do not verify entailment. A cited passage may be related to the topic without supporting the exact claim. Grounding therefore needs a separate claim-to-source check, using NLI or another verifier, before the citation can be trusted.<br />
<em><a href="Home/AI &amp; ML/LLM/Generation.md" class="internal-link">Generation</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What does graph engineering add beyond loop engineering and workflow patterns?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Loop engineering controls progress, verification, budgets, and termination across repeated work. Workflow patterns name reusable shapes such as routing or evaluator-optimizer. Graph engineering makes the chosen shape executable by defining nodes, legal transitions, shared state, merge rules, scheduling assumptions, checkpoints, and recovery behavior. A loop can remain inside one node or appear as a cycle across several nodes.<br />
<em><a href="Home/AI &amp; ML/LLM/Graph Engineering.md" class="internal-link">Graph Engineering</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">Why does an explicit graph not make an agentic system deterministic?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Fixed edges constrain which paths are legal, and deterministic guards can make some transitions reproducible. Nodes may still contain model calls, external APIs, mutable data, or concurrent work whose results vary. The graph makes control flow more inspectable; it does not guarantee the quality or repeatability of the work inside each node.<br />
<em><a href="Home/AI &amp; ML/LLM/Graph Engineering.md" class="internal-link">Graph Engineering</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">Why does checkpointing require idempotent node design?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">A runtime normally checkpoints at a step boundary rather than after every instruction inside a node. If a process stops after performing a side effect but before committing the checkpoint, resume can execute that side effect again. Idempotency keys, upserts, or read-before-write checks make re-execution safe; a checkpoint alone does not provide exactly-once delivery.<br />
<em><a href="Home/AI &amp; ML/LLM/Graph Engineering.md" class="internal-link">Graph Engineering</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">How should prompting, RAG, and fine-tuning be chosen for an LLM system?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">The choice starts with the type of gap shown by evaluation. Prompting is the simplest option when clearer instructions or examples can stabilize the task. RAG fits gaps in current or private knowledge and cases where answers need source evidence. Fine-tuning fits a stable behavior gap, such as format, policy, style, or a narrow task, after prompting has been tested and is still inconsistent. The techniques can be combined: fine-tuning can shape behavior while RAG supplies facts that change.<br />
<em><a href="Home/AI &amp; ML/LLM/LLM.md" class="internal-link">LLM</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What matters when choosing an LLM?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Model size and labels such as "frontier" are only starting points. A frontier model may produce better answers but miss the latency or cost target. A smaller model may look cheap until retries and human escalation are included.<br />
Candidates should be tested on the same representative workload for task quality, safety, reliability, latency, and total cost per successful task. The best choice is the least expensive model that meets all required targets.<br />
<em><a href="Home/AI &amp; ML/LLM/Model Selection and Routing.md" class="internal-link">Model Selection and Routing</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">How do classifier routing and cascading differ, and when is each useful?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">A classifier chooses a model before generation based on the predicted task type or difficulty. It is useful when those signals are reliable and generating a second answer would cost too much or take too long. Its main risk is sending a hard request to a model that cannot handle it.<br />
A cascade starts with one model and decides whether to escalate after checking its answer. It works well when failures can be detected with a cheap, reliable signal, such as schema validation or a groundedness check. Failed first attempts pay for a second generation and add latency.<br />
The patterns can also work together: a classifier can choose the initial route, while a cascade handles answers that fail a quality gate. The complete route should be evaluated for end-to-end quality, cost, and tail latency.<br />
<em><a href="Home/AI &amp; ML/LLM/Model Selection and Routing.md" class="internal-link">Model Selection and Routing</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">Why can LoRA still cause forgetting if the base weights are frozen?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">The deployed output comes from the base plus the adapter’s updates. Narrow adapter training can steer that effective model away from capabilities outside the training distribution. The frozen base makes rollback easy. It does not guarantee unchanged behavior while the adapter is enabled.<br />
<em><a href="Home/AI &amp; ML/LLM/Fine-tuning.md" class="internal-link">Fine-tuning</a></em></p>
</div></div></blockquote></span><h3>Agents</h3><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">When does a workflow fit better than an autonomous agent?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">A workflow fits predictable steps with explicit inputs and outputs. Its fixed control flow is cheaper to run and easier to debug. Autonomy is justified when the steps are not known in advance and the system has a checkable success signal that can catch drift.<br />
<em><a href="Home/AI &amp; ML/LLM/Agents/Agents.md" class="internal-link">Agents</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">How does an autonomous agent accumulate error, and what bounds it?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Each step consumes state produced by earlier steps, so one bad assumption can shape the rest of the run. Iteration caps bound cost, validation gates reject invalid progress, and an escalation path stops the loop when recovery needs outside input. Decision and tool traces make the original divergence visible.<br />
<em><a href="Home/AI &amp; ML/LLM/Agents/Agents.md" class="internal-link">Agents</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What makes a task a good fit for an autonomous agent?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">The control flow must be genuinely open-ended, and progress must still be checkable. Tests, resolution criteria, or source-backed claims give the loop feedback. Vague or delayed outcomes do not. The agent can keep moving while getting further from the goal.<br />
<em><a href="Home/AI &amp; ML/LLM/Agents/Agents.md" class="internal-link">Agents</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">How do the five workflow patterns differ in who controls the next step?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">The difference is how much of the control flow is fixed by the application. Prompt chaining fixes the sequence, routing chooses among predefined branches, and parallelization runs predefined work at the same time. With orchestrator-workers, the model decides the tasks and worker count at runtime. Evaluator-optimizer adds a loop that continues until an acceptance test passes or a limit is reached. The simplest pattern that matches the task is usually easier to test because every extra model-owned decision adds variable cost and makes failures harder to reproduce.<br />
<em><a href="Home/AI &amp; ML/LLM/Agents/Workflow Patterns.md" class="internal-link">Workflow Patterns</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">Why are orchestrator-workers harder to operate than ordinary parallelization even when their diagrams look similar?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Parallelization starts a known set of calls, so coverage, cost, and aggregation can be tested ahead of time. An orchestrator chooses the decomposition and worker count from the input. That flexibility creates variable cost and new failure modes: missing work, overlapping assignments, or a synthesis that cannot reconcile the results. It also makes the pattern a bridge into <a class="internal-link" href="Multi-Agentic Systems">Multi-Agentic Systems</a>, because the model controls the shape of the work.<br />
<em><a href="Home/AI &amp; ML/LLM/Agents/Workflow Patterns.md" class="internal-link">Workflow Patterns</a></em></p>
</div></div></blockquote></span><h4>Evaluation</h4><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">Why can one base model produce very different results on the same benchmark?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">The benchmark runs a model-plus-scaffold system. Planning logic, retry limits, prompts, tool descriptions, and context handling all affect the outcome. Scores from different scaffolds cannot isolate model quality. A fair model comparison keeps the scaffold fixed, then reruns the candidates on the same tasks.<br />
<em><a href="Home/AI &amp; ML/LLM/Agents/Evaluation/Agent Benchmarks.md" class="internal-link">Agent Benchmarks</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">Why should tool selection and argument accuracy be measured separately?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">They fail for different reasons. Choosing the wrong tool usually points to routing or unclear tool descriptions. Choosing the right tool but passing the wrong order ID, filter, or date points to grounding or schema problems. Separate metrics make a result such as 95% selection accuracy and 70% argument accuracy actionable instead of hiding it inside one average. Identifiers and enums can usually be checked against exact references, while free-text arguments often need a semantic check.<br />
<em><a href="Home/AI &amp; ML/LLM/Agents/Evaluation/Tool-Call Evaluation.md" class="internal-link">Tool-Call Evaluation</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">When is reference matching a better trajectory scorer than an LLM judge?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Reference matching fits tasks with a small set of knowable procedures. It is cheap, objective, and can enforce hard boundaries: subset mode proves the agent stayed within an allowed tool set, while superset mode proves required calls occurred. A judge becomes necessary when valid decompositions are too numerous to enumerate, but it adds cost and long-context bias.<br />
<em><a href="Home/AI &amp; ML/LLM/Agents/Evaluation/Trajectory Evaluation.md" class="internal-link">Trajectory Evaluation</a></em></p>
</div></div></blockquote></span><h3>Context Engineering</h3><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">Why does adding more context often make answers worse, not better?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Attention is uneven across a long window, so evidence buried in the middle may be underused. Added tokens also compete with the evidence already present, even when they are loosely relevant. Larger inputs cost more and take longer. The fix is signal density: keep fewer complete chunks, order them deliberately, and measure whether each increase in context improves the answer.<br />
<em><a href="Home/AI &amp; ML/LLM/Context Engineering/Context Engineering.md" class="internal-link">Context Engineering</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What are the main techniques for keeping a long-running agent's context under control?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Context control starts with tracking the token budget on every iteration instead of waiting for the window to fill. Keep a small set of strong evidence and place the best material where the model is likely to use it. Older turns can be compacted into decisions, constraints, and pending work. Tool results should contain only the fields needed for the next step, while bulky state can live outside the window and be loaded through a reference when needed.<br />
<em><a href="Home/AI &amp; ML/LLM/Context Engineering/Context Engineering.md" class="internal-link">Context Engineering</a></em></p>
</div></div></blockquote></span><h4>RAG</h4><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">Why should retrieval cache keys be based on processed query text instead of raw embeddings?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Processed query text and its transformation version are readable, deterministic inputs. Raw embedding bytes change with the model and hide why two entries differ. A translation-version change should produce a new key, and the embedding model version still belongs in the retrieval key because it affects ranking.<br />
<em><a href="Home/AI &amp; ML/LLM/Context Engineering/RAG/Caching.md" class="internal-link">Caching</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">Why is response caching riskier than embedding caching?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">A fixed text-and-model pair produces the same embedding. A response also depends on the prompt template, retrieved evidence, permissions, and generation model. Any of those can change independently, so a response key is easier to under-specify and harder to invalidate safely.<br />
<em><a href="Home/AI &amp; ML/LLM/Context Engineering/RAG/Caching.md" class="internal-link">Caching</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">When is semantic caching safe to deploy, and when should it be avoided?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Semantic caching is defensible when the domain is narrow, queries repeat, false positives have low cost, and a held-out set supports a stable threshold. It should be avoided when a wrong answer can cause harm, conversation state changes meaning, or no threshold separates safe reuse from false hits.<br />

</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">Why does parent-child chunking often improve answer completeness over child-only retrieval?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">

Expanding a match to its parent restores that surrounding evidence before generation. The price is more context and possibly more noise, so parent size still needs evaluation.<br />
<em><a href="Home/AI &amp; ML/LLM/Context Engineering/RAG/Chunking.md" class="internal-link">Chunking</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">When should a team move from recursive to structure-aware chunking?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Move when failed queries repeatedly trace to broken tables, code blocks, or clause-and-exception pairs. Recursive splitting understands separators, not the source format's actual structure. A parser is justified once that blind spot costs more than maintaining it.<br />
<em><a href="Home/AI &amp; ML/LLM/Context Engineering/RAG/Chunking.md" class="internal-link">Chunking</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">Why is semantic chunking not always superior to simpler rule-based approaches?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">It embeds spans during ingestion and relies on a threshold whose distribution changes with the model and corpus. Reliable headings already provide cheaper boundaries. Semantic splitting is useful when topic changes are real but structural markers are absent.<br />
<em><a href="Home/AI &amp; ML/LLM/Context Engineering/RAG/Chunking.md" class="internal-link">Chunking</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">How does monitoring differ from evaluation in a RAG system, and why are both needed?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Evaluation gates a candidate pipeline against a controlled dataset before release. </div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">Why does query translation often improve recall but sometimes hurt precision, and how can the tradeoff be detected?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Query translation raises recall by searching more phrasings, but it lowers precision when a rewrite adds concepts or changes constraints.<br />

</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">When is decomposition a better choice than multi-query, and when does it hurt?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">

<p dir="auto">GraphRAG earns its cost when answers depend on explicit entity relations or paths across many documents. Compliance tracing and architecture impact analysis are examples. <p dir="auto">Every added stage creates another place for quality, latency, or cost to regress. Introduce one pattern against a measured baseline, then keep it only if it fixes a frequent failure. <em><a href="Home/AI &amp; ML/LLM/Context Engineering/RAG/RAG.md" class="internal-link">RAG</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">How can retrieval and generation failures be separated when a RAG answer is wrong?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">

<p dir="auto">The changed positions may sit outside the generator's context. When generation uses only three chunks, a better ordering at positions 4–5 cannot affect the answer. <p dir="auto">It loses when the weaker path adds more noise than useful evidence. A homogeneous scientific corpus may already suit vector search, while keyword results pull marginal matches into the fused list. The extra system earns its cost only if it beats both single-mode baselines on real queries.<br />

</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">Why do vector databases use approximate nearest-neighbor search instead of exact search?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Exact search scores the query against every stored vector, so its work grows linearly with the collection. An ANN index organizes the vectors so a query visits only the most promising parts of the search space, which cuts latency and compute. The tradeoff is that it can miss some true nearest neighbors, so recall must be compared with brute-force ground truth at the required latency.<br />

<p dir="auto">An average hides which queries improved and which regressed. A gain on a large, easy segment can outweigh a severe drop for one tenant or language. Slice metrics along dimensions that change the retrieval distribution, and treat a material segment drop as a failure. The useful granularity is the smallest one with enough labeled examples to produce a stable signal.<br />

<p dir="auto">Faithfulness of 0.91 says the model usually uses the context it receives. Context Recall of 0.54 says retrieval omits much of the required evidence, so retrieval is the first bottleneck to test. </div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">Why decompose RAG evaluation into separate retrieval, generation, and end-to-end layers?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">The layers fail for different reasons and need different fixes. Retrieval scoring shows whether relevant evidence arrived. Generation scoring checks whether the answer follows that evidence, while the end-to-end score records whether the task was solved. <p dir="auto">RAG adds retrieval relevance, ranking quality, and faithfulness to the evidence placed in context. It also needs labels for queries with several acceptable chunks. <p dir="auto">Classify the evidence relationship first. Substitutable chunks need HitRate@k and often MRR because any early hit succeeds. </div></div></blockquote></span><h3>Harness Engineering</h3><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">When should a tool remain an in-process function instead of becoming an MCP server?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Function calling and MCP are not direct alternatives, because an MCP tool can still be presented to the model as a function. The real decision is whether the tool needs a separate reusable server boundary. Keeping it in process is simpler when it belongs to one application, depends on private application state, or would expose sensitive business logic through a broader interface.<br />
<em><a href="Home/AI &amp; ML/LLM/Harness Engineering/Model Context Protocol.md" class="internal-link">Model Context Protocol</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What additional security risks appear when a model uses tools from an MCP server?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">An MCP server still has the usual API risks, but its tool names and descriptions also become model context, and the model may request an operation after reading untrusted content. With HTTP, MCP authorization can restrict access to the server and enforce OAuth audience and scopes; insufficient scope can trigger another authorization step. Those scopes do not automatically define whether a caller may run each business operation or access a particular tenant's data. The server still needs per-tool authorization, input validation, tenant isolation, rate limits, and audit logging.<br />
<em><a href="Home/AI &amp; ML/LLM/Harness Engineering/Model Context Protocol.md" class="internal-link">Model Context Protocol</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What does harness engineering control that context engineering does not?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Context engineering decides what information the model receives. Harness engineering decides what the runtime allows the model to do with that information: which tools are exposed, what permissions they have, how calls are validated, and where execution is sandboxed or stopped for approval. Tool schemas and results connect the two areas because they consume context, but capability and permission decisions still belong to the harness. Loop engineering then controls whether another turn is allowed.<br />
<em><a href="Home/AI &amp; ML/LLM/Harness Engineering/Harness Engineering.md" class="internal-link">Harness Engineering</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">Why does harness quality deserve as much investment as prompt quality for agent reliability?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Agents reuse the harness on every iteration. An ambiguous tool or vague error can redirect one step and then contaminate every later step. A precise contract helps the model recover, and repairing it improves every run that shares the surface.<br />
<em><a href="Home/AI &amp; ML/LLM/Harness Engineering/Harness Engineering.md" class="internal-link">Harness Engineering</a></em></p>
</div></div></blockquote></span><h4>Tooling</h4><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">Why do hierarchical instruction files often outperform a single giant root file?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">The root file can hold rules that apply to the whole repository, while a local file adds the build command or dependency rule for one subtree when the runtime supports path-based loading. This keeps unrelated guidance out of the model's context and makes the active instructions more specific to the files being changed. The hierarchy works only when precedence is clear and local rules refine the root instead of silently contradicting it.<br />
<em><a href="Home/AI &amp; ML/LLM/Harness Engineering/Tooling/Agent Instructions.md" class="internal-link">Agent Instructions</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What controls reduce production risk when adopting coding agents?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Start by limiting the task, the tools the agent can call, and the number of iterations it can run. Destructive or external actions need code-enforced approval before execution, while hooks and CI should run deterministic checks. Repository instructions capture architectural rules that tests cannot enforce. Before merge, the diff still needs review and the claimed behavior needs fresh test or build evidence, regardless of which model produced the change.<br />
<em><a href="Home/AI &amp; ML/LLM/Harness Engineering/Tooling/Coding Agents.md" class="internal-link">Coding Agents</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">Why is tool design often more impactful than prompt engineering in agentic systems?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">A tool contract is reused at every call site and every loop iteration. Ambiguous selection, malformed arguments, or an opaque error can redirect all later steps. Fixing the interface removes that failure mode across prompts, while a prompt workaround depends on the model remembering an exception each time.<br />
<em><a href="Home/AI &amp; ML/LLM/Harness Engineering/Tooling/Tool Design.md" class="internal-link">Tool Design</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What determines whether related operations should use one broad tool or several narrow tools?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Separate tools make sense when operations need different descriptions, input schemas, or permissions. Closely related actions can stay together when one clear contract covers them without a long list of unrelated optional parameters. Narrow tools make arguments easier to generate, but a large catalog makes tool selection harder. Routing or filtering can limit the tools shown for each request, and selection and argument accuracy should be measured separately.<br />
<em><a href="Home/AI &amp; ML/LLM/Harness Engineering/Tooling/Tool Design.md" class="internal-link">Tool Design</a></em></p>
</div></div></blockquote></span><h3>Loop Engineering</h3><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What does ReAct add to chain-of-thought reasoning when a task needs external knowledge?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Chain-of-thought reasoning still works with information already available to the model. ReAct can pause that reasoning to search, call an API, or run a calculation, then use the observed result in the next decision. This helps when the answer depends on current or missing evidence, but it does not guarantee a better result. Each action adds another model round trip, grows the context, and creates another place for a tool or interpretation error.<br />
<em><a href="Home/AI &amp; ML/LLM/Loop Engineering/Agent Loop.md" class="internal-link">Agent Loop</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">Which safeguards must be enforced outside the model, and what failure does each contain?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">A per-request iteration cap contains non-terminating behavior. Token and cost budgets stop context growth before it becomes an outage or an unexpected bill. Tool validation blocks unknown functions and malformed arguments before they reach a side-effecting boundary. Prompt instructions can help, but none of these controls can depend on the model obeying them.<br />
<em><a href="Home/AI &amp; ML/LLM/Loop Engineering/Agent Loop.md" class="internal-link">Agent Loop</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What does loop engineering add on top of a model with tools, and why is it its own discipline?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">A model with tools can still be a single call. Loop engineering adds the runtime that repeats observe → decide → act until a checkable stop condition. It owns budgets and verification between turns, which determines whether an early mistake is corrected or amplified.<br />
<em><a href="Home/AI &amp; ML/LLM/Loop Engineering/Loop Engineering.md" class="internal-link">Loop Engineering</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What are the main ways to bound a loop, and why are prompt-level stop instructions not enough?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">The runtime needs a hard iteration cap, a cumulative token or cost budget, and a stop condition it can verify. Prompt instructions are advisory, so they cannot replace those limits. At the cap, return an explicit partial result or escalate instead of truncating silently. The unbounded run documented in <a class="internal-link" href="Agent Loop">Agent Loop</a> shows the failure mode: 369 repeated tool calls consumed 9.7M tokens without converging.<br />
<em><a href="Home/AI &amp; ML/LLM/Loop Engineering/Loop Engineering.md" class="internal-link">Loop Engineering</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">How do loop engineering and context engineering divide the work of managing a long run's history?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Context engineering decides what belongs in the window and what a summary must preserve. Loop engineering decides when to compact, offload artifacts, or stop. Durable state such as a plan file bridges them by surviving compaction and keeping later iterations tied to the original goal.<br />
<em><a href="Home/AI &amp; ML/LLM/Loop Engineering/Loop Engineering.md" class="internal-link">Loop Engineering</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">When is multi-agent coordination worth the added complexity?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Multi-agent coordination makes sense when separate contexts keep unrelated work apart, independent tasks can run in parallel, or specialists need tools or instructions that would conflict inside one agent. The extra agents also mean more tokens, handoffs, and traces to debug, so the design should show a clear improvement in quality or latency over a single agent.<br />
<em><a href="Home/AI &amp; ML/LLM/Loop Engineering/Multi-Agentic Systems.md" class="internal-link">Multi-Agentic Systems</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What is the benefit of keeping related context with one agent?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Keeping related evidence and decisions in one working context lets the agent complete connected work without rebuilding the same background after each handoff. Splitting that work between agents creates more transfers and more chances to lose details. The tradeoff is that each agent owns a broader part of the work.<br />
<em><a href="Home/AI &amp; ML/LLM/Loop Engineering/Multi-Agentic Systems.md" class="internal-link">Multi-Agentic Systems</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What makes multi-agent failures difficult to trace?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">A bad output can pass through several agents before the failure becomes visible. A handoff may contain a false claim that looks valid, and parallel agents may repeat that claim in several places. Debugging therefore needs the full handoff history, the source of each artifact, and limits such as token or turn budgets for the whole run, not just separate agent logs.<br />
<em><a href="Home/AI &amp; ML/LLM/Loop Engineering/Multi-Agentic Systems.md" class="internal-link">Multi-Agentic Systems</a></em></p>
</div></div></blockquote></span><h3>Prompt Engineering</h3><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">When is prompt chaining a better fit than one large prompt?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Chaining fits when a task has real stages and an intermediate result changes what should happen next. Each stage should have a clear output contract, so invalid data can be stopped before it reaches the following call and failures can be traced to one step. That control has to justify the extra latency, token cost, and risk of errors passing between calls. If the task is simple and no intermediate result needs separate validation, one prompt is usually easier to operate.<br />
<em><a href="Home/AI &amp; ML/LLM/Prompt Engineering/Prompt Composition.md" class="internal-link">Prompt Composition</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What is a practical meta prompting workflow for improving a weak prompt?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">A useful workflow starts with real failures rather than a general request to make the prompt better. Group the failures by cause, then ask for a revision that addresses those causes and states a clear output contract. Compare the candidate with the current prompt on held-out cases, not only on the examples used to create it. Version the prompt and evaluator together, and keep a rollback threshold in case the revision fixes known failures but hurts normal inputs.<br />
<em><a href="Home/AI &amp; ML/LLM/Prompt Engineering/Prompt Composition.md" class="internal-link">Prompt Composition</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">How should a task move from zero-shot to one-shot or few-shot prompting?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Zero-shot is the baseline when instructions and labels define the task clearly. One example is useful when the main failure is the output shape. Few-shot prompting earns its extra tokens when examples express decision boundaries better than prose. The final prompt should keep the smallest demonstration set that wins on a representative evaluation set, because every example adds cost and another artifact that can drift.<br />
<em><a href="Home/AI &amp; ML/LLM/Prompt Engineering/In-Context Learning.md" class="internal-link">In-Context Learning</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What are the main failure modes of few-shot prompting?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Few-shot behavior can shift when examples are reordered, reformatted, or run on a different model. Long demonstrations also consume context, while examples that do not match production traffic create false confidence. Examples cannot reliably supply missing external facts or control a long multi-step process. Those failures call for retrieval, decomposition, or training rather than simply adding more shots.<br />
<em><a href="Home/AI &amp; ML/LLM/Prompt Engineering/In-Context Learning.md" class="internal-link">In-Context Learning</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">Why must prompt structure and model settings be designed together?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">The prompt defines the task, context, constraints, and expected output, while model settings control sampling and output limits. Clear instructions can still produce unstable results when sampling is too random for the task. Conservative settings cannot repair an ambiguous instruction or a missing output contract. Both parts should be tested together on the same task-specific evaluation set because changing either one can change quality, consistency, latency, and cost.<br />
<em><a href="Home/AI &amp; ML/LLM/Prompt Engineering/Prompt Engineering.md" class="internal-link">Prompt Engineering</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">When is few-shot prompting a better fit than pure instruction prompting?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Few-shot prompting is useful when the expected meaning, label boundary, or output convention is easier to demonstrate than to describe. A small set of representative examples can show how close cases should be handled and make repeated outputs more consistent. Examples do not replace a schema when the shape must be strict. Start with the smallest set that improves held-out results, then add edge cases only when evaluation shows a real gap because every example consumes context.<br />
<em><a href="Home/AI &amp; ML/LLM/Prompt Engineering/Prompt Engineering.md" class="internal-link">Prompt Engineering</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">How can an accurate but verbose and expensive prompt be tightened?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">First identify whether the cost comes from repeated instructions, unnecessary examples, oversized context, or a verbose output contract. Remove duplicated input and state the required length and shape directly. <code>max_tokens</code> is a safety cap rather than the main way to request a concise answer because a low cap can truncate a valid response; stop sequences help only when the output has a reliable delimiter. Compare token usage, task quality, and truncation or failure rates after each change so a cheaper prompt does not quietly become less accurate.<br />
<em><a href="Home/AI &amp; ML/LLM/Prompt Engineering/Prompt Engineering.md" class="internal-link">Prompt Engineering</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">When does Chain-of-Thought help, and when can it make a result worse?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Chain-of-Thought can help when a task has intermediate state that can be expressed as a sequence of smaller decisions. It adds little to simple retrieval or extraction, where the extra tokens mainly create more room for drift. A wrong assumption near the start can shape the rest of the trace, and a fluent explanation still does not prove the answer is correct. The technique earns its cost when the intermediate steps improve measured results or expose something that can be checked independently.<br />
<em><a href="Home/AI &amp; ML/LLM/Prompt Engineering/Reasoning Techniques.md" class="internal-link">Reasoning Techniques</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">When does Tree of Thoughts justify its cost over Chain-of-Thought or self-consistency?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Tree of Thoughts fits a real search problem where candidate states can be generated, evaluated, revisited, and abandoned when they lead to a dead end. Planning and combinatorial search can have that shape; extraction usually does not. Its cost grows with the branching factor and depth, and a weak evaluator can keep the wrong branches. If a direct call or deterministic tool already meets the evaluation target, the tree adds work without improving the result.<br />

</div></div></blockquote></span><h3>Safety</h3><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What is the minimum useful guardrail set for a production LLM application?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Start with task-scoped tools, authorization outside the model, strict output parsing, request budgets, and a refusal or escalation path. Add policy classifiers and human approval where the harm warrants their latency. Prompt-injection detection is useful telemetry, but it cannot replace the permission boundary.<br />
<em><a href="Home/AI &amp; ML/LLM/Safety/Guardrails.md" class="internal-link">Guardrails</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">Why can an LLM still hallucinate when using RAG?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">RAG gives the model context, but it does not prove that the answer follows from it. The source may not contain the fact, retrieval may miss the right passage, or the model may ignore the passage and add unsupported details. Retrieval quality and answer faithfulness should be measured separately so the failing stage is clear.<br />
<em><a href="Home/AI &amp; ML/LLM/Safety/Hallucinations.md" class="internal-link">Hallucinations</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">Why can preference tuning make an answer sound better without making it more factual?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Preference data may reward agreement, confidence, or style without checking whether a claim is supported. The model can then produce a polished answer that accepts a false premise. Factual accuracy and calibration still need separate evaluation from preference scores.<br />

<p dir="auto">Data drift changes P(X), such as a new language appearing in support traffic. Concept drift changes P(Y|X), such as yesterday's fraud cues becoming normal behavior. </div></div></blockquote></span><h3>Evaluation</h3><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What does ROC-AUC show about a classifier?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">ROC-AUC shows how well the classifier ranks positive cases above negative cases across all thresholds. For example, an ROC-AUC of 0.8 means a randomly chosen positive receives a higher score than a randomly chosen negative about 80% of the time, with a tie counted as half.<br />
It does not choose a production threshold or show whether the predicted scores are calibrated probabilities.<br />

</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What types of classification problems are better evaluated with PR-AUC than ROC-AUC?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">PR-AUC is usually more useful when the positive class is rare and the system acts on positive predictions, as with fraud alerts or anomaly review. In these cases, false positives fill the review queue, and precision shows that cost directly.<br />
The score must still be compared with the positive rate in the evaluation data because the PR-AUC baseline changes with prevalence.<br />

<p dir="auto">Supervised learning receives an external target for each example. Self-supervised learning derives a proxy target from the input itself, such as a hidden or next token. </div></div></blockquote></span><h1 id="computer-science">Computer Science</h1><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">Why does Big O drop constant factors and lower-order terms?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Big O describes growth as <code>n → ∞</code>, where the fastest-growing term dominates. <code>n² + 100n + 500</code> is <code>O(n²)</code> because the quadratic term eventually outweighs the rest.<br />
<em><a href="Home/Computer Science/Big O Notation.md" class="internal-link">Big O Notation</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What is the difference between average-case and amortised complexity?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Average-case complexity takes an expectation over a distribution of inputs. A hash lookup is <code>O(1)</code> average when keys spread across buckets. Amortised complexity spreads expensive operations across a sequence on one structure. Dynamic-array append is <code>O(1)</code> amortised because many cheap appends pay for the occasional <code>O(n)</code> resize.<br />
<em><a href="Home/Computer Science/Big O Notation.md" class="internal-link">Big O Notation</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">When does algorithmic complexity matter less than constant factors?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">When input sizes are small and bounded (e.g., iterating over 10 HTTP headers), constant factors and cache locality dominate. A theoretically better algorithm with higher overhead (setup cost, memory indirection) can be slower than a simpler one on small inputs.<br />
This is why .NET's <code>Array.Sort</code> uses insertion sort for small subarrays inside its introspective sort implementation.<br />
<em><a href="Home/Computer Science/Computer Science.md" class="internal-link">Computer Science</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What determines whether a performance problem needs a different data structure or a different algorithm?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">The dominant operation is the starting point. A <code>HashSet&lt;T&gt;</code> removes repeated membership scans, while a <code>SortedSet&lt;T&gt;</code> keeps the set ordered as items are added or removed. If a change affects an item's sort order, remove it and add it again. The algorithm becomes the next target when the representation is fixed by an external format or the chosen structure still leaves too much work in each operation.<br />
<em><a href="Home/Computer Science/Computer Science.md" class="internal-link">Computer Science</a></em></p>
</div></div></blockquote></span><h2 id="computer-science-algorithms">Algorithms</h2><h3>Paradigms</h3><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What turns brute-force enumeration into backtracking?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">A feasibility test on the partial candidate. Brute force waits until a configuration is complete. Backtracking checks after each choice and discards every completion that shares a rejected prefix.<br />
<em><a href="Home/Computer Science/Algorithms/Paradigms/Backtracking.md" class="internal-link">Backtracking</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What changes between memoization and tabulation if the recurrence is the same?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Evaluation order and control flow. Memoization starts at the target, follows recursive dependencies, and stores states on demand. Tabulation starts at the base cases and fills states in a fixed order. Their asymptotic work matches when they visit the same states. Tabulation avoids call-stack cost, while memoization may skip states the target never reaches.<br />
<em><a href="Home/Computer Science/Algorithms/Paradigms/Dynamic Programming.md" class="internal-link">Dynamic Programming</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What is the relationship between memoization and dynamic programming?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Memoization is DP's top-down implementation: write the recurrence and cache each subproblem's result. Bottom-up tabulation solves the same dependency graph iteratively. Memoization evaluates only states reached by recursion, while tabulation usually fills a planned table in dependency order. Repeated states make the cache useful. Optimal substructure is a separate requirement for optimization problems.<br />
<em><a href="Home/Computer Science/Algorithms/Paradigms/Memoization.md" class="internal-link">Memoization</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">Why must a memoised function be pure, and what breaks if it isn't?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">A cache hit returns a stored result without running the function again. If the output also depends on a global value, the clock, or an I/O read, the stored result may describe conditions that no longer hold. Any expected side effect is skipped as well. Safe memoization therefore requires same-input-same-output behavior and no observable side effects.<br />
<em><a href="Home/Computer Science/Algorithms/Paradigms/Memoization.md" class="internal-link">Memoization</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What is the most common correctness bug when memoising a recurrence?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">An incomplete cache key. If a <code>(i, capacity)</code> knapsack state is cached on <code>i</code> alone, two different subproblems map to the same entry and the second lookup can return the wrong value. The key must represent the full state, which is the same requirement DP calls state design.<br />

</div></div></blockquote></span><h1 id="data-persistence">Data Persistence</h1><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What determines the isolation level needed for a read-modify-write transaction?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">The required protection depends on the invariant and on every row or predicate used to make the decision. </div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">Why is a bigger connection pool often worse, not better?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Each connection consumes server resources. After the useful database concurrency is saturated, additional queries wait on CPU, I/O, or locks inside the engine, so latency rises without a matching throughput gain. <em><a href="Home/Data Persistence/Connection Pooling.md" class="internal-link">Connection Pooling</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What factors determine whether a new service should use SQL or a NoSQL store?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">The decision starts with the data model, required guarantees, and main access patterns. <p dir="auto">Asynchrony is about not blocking while work is waiting. During asynchronous I/O, the method can pause without keeping a worker thread idle, then continue later, possibly on the same thread.<br />
Multithreading is about executing work on multiple threads at the same time, usually for CPU-bound work. An application can be asynchronous while using only one thread, but CPU-bound work still needs a thread to execute it.<br />
<em><a href="Home/Programming/NET/CSharp/Concurrency and Parallelism/Async Await.md" class="internal-link">Async Await</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What is the difference between <code>await</code> and using <code>Task.Result</code>?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Both return the task's result, but they wait differently. If the task is not complete, <code>await</code> pauses the method without blocking the current thread. The method continues when the task finishes, using the captured <code>SynchronizationContext</code> when one exists.<br />
<code>Task.Result</code> blocks the current thread until the task completes. This can cause a deadlock when the continuation needs to return to that same thread. It also wraps errors in <code>AggregateException</code>, while <code>await</code> throws the original exception.<br />

</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">When is <code>ConfigureAwait(false)</code> appropriate?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">

UI code usually keeps context capture when it needs to update controls. ASP.NET Core normally has no custom <code>SynchronizationContext</code>, so using <code>ConfigureAwait(false)</code> there usually changes little, and <code>HttpContext</code> does not depend on that context.<br />

<p dir="auto">While I/O is pending, the asynchronous operation pauses and returns its worker thread to the pool. That thread can process another request instead of sitting idle. A server with 100 threads can therefore keep thousands of I/O-bound requests in progress, as long as those threads are released during each wait. This improves concurrency for I/O-bound work; it does not make CPU-bound work require fewer threads.<br />

</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">When is <code>Task.Run</code> useful in async code?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto"><code>Task.Run</code> is useful for CPU-bound work that should run on a thread-pool thread, for example to keep a UI thread responsive. It should not wrap an I/O API that is already asynchronous. That adds another scheduling step without making the I/O finish sooner.<br />

</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What does a bounded <code>Channel&lt;T&gt;</code> provide that <code>SemaphoreSlim</code> does not?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">

A channel therefore fits producer-consumer handoff, while a semaphore fits throttling access to an operation.<br />

<p dir="auto">An unbounded channel never slows a producer because of capacity. </div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What is the difference between concurrency and parallelism in practice?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Concurrency means several operations are in progress during the same period, even if one thread takes turns running them. Parallelism means operations execute at the same time on multiple cores. Asynchronous I/O uses concurrency so a thread is not blocked while an external operation is pending. CPU-bound work uses parallelism when splitting the calculation across cores reduces its elapsed time.<br />

</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What should be checked before choosing <code>Task</code>, <code>lock</code>, <code>Parallel</code>, or <code>Channel</code>?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">First check what the work spends time doing and who is responsible for finishing it. I/O-bound work usually needs asynchronous APIs so threads are not blocked. </div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">When is <code>SemaphoreSlim</code> a better fit than <code>lock</code>?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">

<p dir="auto">A <code>Task</code> represents an operation that may finish later and records whether it completed, failed, or was canceled. A thread is a resource that executes code. A task for asynchronous I/O can remain incomplete while no managed thread is assigned to it; a thread is needed only when code starts the operation or resumes after completion.<br />

</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">When is <code>Task.Run</code> appropriate in ASP.NET Core?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto"><code>Task.Run</code> can move CPU-bound work to a thread-pool thread, but it does not add CPU capacity. Under load, those extra work items compete with request processing and can reduce throughput. It should not wrap I/O APIs that are already asynchronous. Long or expensive work usually belongs behind a bounded background queue or in a separate service instead of running inside the request.<br />

<p dir="auto"><code>ValueTask</code> is useful in a measured hot path where operations often complete synchronously and allocating a completed <code>Task</code> is a real cost. </div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What is ThreadPool starvation and how does it usually start?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">ThreadPool starvation means queued callbacks and continuations wait too long because too few worker threads are available, even though the CPU is not fully busy doing useful work. <p dir="auto"><code>ThreadPool.SetMinThreads</code> is worth testing when measurements show that work is waiting for the pool to add workers during a burst. It is not a fix for CPU saturation, a slow downstream service, or workers blocked by sync-over-async code.</p>
<p dir="auto">Change it under a representative load test and watch queue length, worker count, CPU, memory, and tail latency. The value is a threshold below which the pool can add workers without its normal delay; it does not create that many threads in advance.<br />

<p dir="auto">Wrap an exception when code crosses a boundary and the caller needs context that the original failure does not provide. For example, a repository can translate a database exception into an order-saving exception that the application layer understands. </div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">When should a type be a <code>struct</code>, <code>class</code>, or <code>record class</code>?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Start with assignment and equality semantics. A <code>struct</code> fits a small logical value that should be copied as a whole. A conventional class fits an entity whose identity stays the same while its state changes. A <code>record class</code> fits reference-typed data whose contents define equality. After that, size, mutation, boxing, and measured allocation cost can rule out a choice that looked correct from the data model alone.<br />
<em><a href="Home/Programming/NET/CSharp/Fundamentals/Types/Types.md" class="internal-link">Types</a></em></p>
</div></div></blockquote></span><h3>Runtime</h3><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">How do managed and unmanaged code differ, and why does interop require careful lifetime management?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Managed code runs under the CLR, which uses metadata to provide services such as garbage collection, type checks, and exception handling. Unmanaged code runs as native code and follows the platform's ABI. A P/Invoke or other interop signature must match that ABI, including the calling convention, data layout, and encoding. A mismatch can corrupt the arguments, returned data, or call stack.</p>
<p dir="auto">Resource lifetime is a separate contract defined by the native API: which side allocates the resource, which side owns it, and which function releases it. The GC can track a managed wrapper, but it does not know that native ownership contract. An owned handle should normally be placed in <code>SafeHandle</code> and released through deterministic disposal. The wrapper then keeps the handle valid during native calls and releases it once with the correct native operation.<br />
<em><a href="Home/Programming/NET/Runtime/Common Language Runtime.md" class="internal-link">Common Language Runtime</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">How does the CLR run IL, and when does JIT or Native AOT make more sense?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Most .NET builds store IL together with type metadata in an assembly. The CLR loads that assembly, and a JIT deployment compiles each method when it is first used. Tiered compilation can later replace frequently executed methods with more optimized code. This adds first-use work, but it allows runtime optimization and supports dynamic-code features.</p>
<p dir="auto">Native AOT compiles the application at publish time, so the deployed process has no JIT compilation step. It can be a better fit when measured startup time or footprint matters, but dependencies must survive trimming and AOT analysis, and features that require runtime code generation may not work.<br />
<em><a href="Home/Programming/NET/Runtime/Common Language Runtime.md" class="internal-link">Common Language Runtime</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">Why can generation 0 be collected without scanning every generation 2 object?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">The collector starts from normal GC roots, but it also needs to find references from old objects to young ones. A write barrier records the older heap ranges where those references may have been written. During a generation 0 collection, the GC scans those recorded ranges, called dirty cards, instead of walking every generation 2 object. Young objects referenced by older ones are still preserved without paying for a full old-generation scan.<br />
<em><a href="Home/Programming/NET/Runtime/Garbage Collector.md" class="internal-link">Garbage Collector</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">Why can process memory remain high after a generation 2 collection?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">A generation 2 collection removes objects that are no longer reachable; it cannot remove live object graphs held by caches, static fields, or other roots. Pinned objects and swept heap regions can also leave gaps that are free to the GC but difficult to reuse. Finally, the runtime may keep committed heap memory for later allocations instead of returning it to the operating system immediately. A completed collection therefore does not guarantee that the process working set will shrink.<br />
<em><a href="Home/Programming/NET/Runtime/Garbage Collector.md" class="internal-link">Garbage Collector</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">Can a .NET application leak memory even though it has garbage collection?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Yes. The GC reclaims managed objects only after they become unreachable. If a static cache, event subscription, or long-lived collection still points to an object that is no longer useful, the object and everything it references remain alive. The collector is doing its job, but the application is keeping the object alive for too long.</p>
<p dir="auto">The GC does not own native memory or operating-system handles. They leak when their owner never releases them, usually through <code>Dispose()</code> or a safe wrapper such as <code>SafeHandle</code>. Repeated process growth is a reason to investigate, but a managed root path or an unreleased native allocation is what proves the leak.<br />
<em><a href="Home/Programming/NET/Runtime/Memory Leaks.md" class="internal-link">Memory Leaks</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">Why is <code>using</code> needed when .NET already has garbage collection?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">The GC manages managed memory and decides for itself when to run. Resources such as file handles, sockets, operating-system handles, and unmanaged buffers often need to be released as soon as their owner is finished with them.</p>
<p dir="auto">A <code>using</code> statement gives that cleanup a clear scope. It has <code>try</code>/<code>finally</code> semantics, so <code>Dispose()</code> is called when control leaves the scope, including when an exception is thrown.<br />
<em><a href="Home/Programming/NET/Runtime/Memory Leaks.md" class="internal-link">Memory Leaks</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">How do <code>IDisposable</code> and a finalizer differ?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto"><code>IDisposable</code> provides explicit cleanup through <code>Dispose()</code>. The owner can call it directly or use <code>using</code>, so the resource is released at a known point.</p>
<p dir="auto">A finalizer is a fallback that the runtime may run after the object becomes unreachable. Its timing is unpredictable, and it is not guaranteed during abrupt process termination. A custom finalizer is normally needed only when a type directly owns an unmanaged resource and no suitable <code>SafeHandle</code> exists. After explicit cleanup succeeds, <code>Dispose()</code> calls <code>GC.SuppressFinalize(this)</code> to avoid the extra finalization work.<br />
<em><a href="Home/Programming/NET/Runtime/Memory Leaks.md" class="internal-link">Memory Leaks</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">How does the .NET dispose pattern work?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto"><code>Dispose()</code> releases the resources owned by the object and must be safe to call more than once. In an inheritable type, the public method normally calls a protected <code>Dispose(bool disposing)</code> method and then suppresses finalization. The <code>disposing</code> flag is <code>true</code> during explicit cleanup, when owned managed disposables can also be released.</p>
<p dir="auto">A finalizer is added only when the type directly owns an unmanaged resource that cannot be delegated to a safe wrapper. Its path calls <code>Dispose(false)</code>, which releases only that unmanaged state because other managed objects may already have been finalized.<br />
<em><a href="Home/Programming/NET/Runtime/Memory Leaks.md" class="internal-link">Memory Leaks</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What does the CLR do when an application starts, and why does startup behavior matter?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">A native host selects and starts the runtime, then the loader resolves the entry assembly and dependencies. Executed methods use ReadyToRun code when available or are JIT-compiled. Tiering can replace those bodies later. Assembly loading, static initialization, JIT work, and dependency setup can all appear in cold-start latency, so traces must separate them.<br />
<em><a href="Home/Programming/NET/Runtime/Runtime.md" class="internal-link">Runtime</a></em></p>
</div></div></blockquote></span><h1 id="security">Security</h1><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">How are symmetric and asymmetric cryptography used together in a real system?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Symmetric authenticated encryption handles bulk data because it is efficient and protects both confidentiality and integrity. Public-key encryption is limited to the small payloads and protocols it was designed for. Signatures provide public verification, while authenticated key agreement establishes a fresh shared secret. Protocols such as TLS and envelope encryption combine these roles instead of choosing one family for the whole job.<br />
<em><a href="Home/Security/Encryption.md" class="internal-link">Encryption</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">Why is SHA-256 alone unsuitable for password storage?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">SHA-256 is fast and gives an offline attacker a cheap guess test. Password verifiers need a unique salt and an adaptive password-hashing function whose CPU and memory costs are tuned for the deployment and raised as hardware improves.<br />
<em><a href="Home/Security/Hashing.md" class="internal-link">Hashing</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">How do a hash, an HMAC, and a digital signature differ?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">A hash is keyless. Adversarial integrity depends on authenticating the expected digest. HMAC authenticates within a shared-secret group, where every verifier can also create tags. A digital signature gives one private-key holder the signing capability while allowing public verification, provided the verification key is trusted.<br />
<em><a href="Home/Security/Hashing.md" class="internal-link">Hashing</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What does a salt protect against, and why must it be unique per user?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">A salt prevents one precomputed table or one computed guess from being reused across many stored verifiers. It is public and stored with the verifier. Each credential needs a distinct random salt so equal passwords do not produce equal stored values.<br />
<em><a href="Home/Security/Hashing.md" class="internal-link">Hashing</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">How should a .NET application prevent SQL injection?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Keep untrusted values out of SQL text by using parameterized APIs. Dynamic identifiers such as a sort column cannot normally be parameters, so map them from a closed allowlist. ORM safety depends on the exact API: LINQ and parameterizing raw-SQL methods differ from APIs that accept already constructed SQL text. Least-privilege database permissions reduce impact but do not repair concatenation.<br />
<em><a href="Home/Security/OWASP.md" class="internal-link">OWASP</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What protection does a pepper add, and what does it cost?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">A pepper kept outside the password table can prevent a database-only thief from testing guesses. It creates another high-value secret and a rotation problem: replacing it for an existing verifier normally requires the user's password or a reset. It cannot compensate for a fast KDF.<br />
<em><a href="Home/Security/Password Storage.md" class="internal-link">Password Storage</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What should happen when a secret is accidentally committed and pushed?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Treat the secret as compromised and revoke or rotate it immediately. Update the affected workloads through the normal secret-delivery path, then verify that the old value is rejected. Check access logs and usage for signs of abuse. Removing the value from the current file and rewriting repository history can reduce future exposure, but neither action replaces revocation because copies may already exist in clones, caches, logs, or alerts.<br />
<em><a href="Home/Security/Secrets Management.md" class="internal-link">Secrets Management</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">How do authentication and authorization work together when handling a request?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Authentication establishes who or what is making the request and produces a principal. Authorization then checks whether that principal may perform the requested action on the specific resource in the current context. A valid identity does not grant access to every resource, so both checks are required.<br />
<em><a href="Home/Security/Security.md" class="internal-link">Security</a></em></p>
</div></div></blockquote></span><h2 id="security-authentication">Authentication</h2><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">Why is Basic Auth unsafe over HTTP?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Base64 is reversible encoding. Without TLS, every observer on the path can recover the reusable password. TLS protects it only to the termination point. The credential remains exposed to the client, verifier, trusted proxies, and any system that records the header.<br />
<em><a href="Home/Security/Authentication/Basic Auth.md" class="internal-link">Basic Auth</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">When is Basic Auth acceptable in production?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">It can be acceptable for a constrained integration that requires Basic and supports TLS across every hop, a unique vaulted credential, narrow authorization, rotation, rate limiting, and header redaction. A shared password across many clients or an interactive user's primary password creates an unnecessarily large compromise boundary.<br />
<em><a href="Home/Security/Authentication/Basic Auth.md" class="internal-link">Basic Auth</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What is the difference between role-based and resource-based authorization?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Role-based authorization evaluates assigned roles without needing the target instance. Resource-based authorization includes the loaded object's attributes or relationships in the decision. Roles work well as coarse gates. Resource checks enforce ownership, tenancy, or object state.<br />
<em><a href="Home/Security/Authentication/Resource-based Auth.md" class="internal-link">Resource-based Auth</a></em></p>
</div></div></blockquote></span><h1 id="software-architecture">Software Architecture</h1><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What factors determine whether a system should use a monolith, a modular monolith, or microservices?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">A monolith keeps one deployment and local transactions, so it usually fits a small team while domain boundaries are still changing. A modular monolith adds enforced module boundaries without introducing network failures or separate operations. It is a safer default when one deployment is not slowing delivery.</p>
<p dir="auto">Microservices fit stable boundaries that repeatedly need independent deployment, scaling, or ownership. That independence comes with remote calls, separate data ownership, eventual-consistency workflows, and distributed observability. Strong module boundaries make a later extraction safer, but they do not remove those costs.<br />
<em><a href="Home/Software Architecture/Software Architecture.md" class="internal-link">Software Architecture</a></em></p>
</div></div></blockquote></span><h2 id="software-architecture-application-architecture">Application Architecture</h2><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">How should a small CRUD service with simple domain rules be structured if growth is expected?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Expected growth alone is not enough reason to start with the full ceremony of Clean Architecture. A layered structure is usually sufficient, provided domain logic does not leak into controllers or infrastructure code. Stricter inward dependency rules become useful when valuable business policy is repeatedly coupled to a framework, database, or external service. Ports and adapters should earn their cost through faster tests or clearer change isolation, not through the possibility that the service may become complex later.<br />
<em><a href="Home/Software Architecture/Application Architecture/Application Architecture.md" class="internal-link">Application Architecture</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">How does Clean Architecture differ from traditional N Layer, and when does the extra indirection pay off?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Traditional N Layer commonly points dependencies from UI through business logic to data access. Clean Architecture points source dependencies toward policy instead, so inner layers own the contracts that outer adapters implement. The extra boundary pays off when business rules are valuable, isolated tests matter, or infrastructure is likely to change. A short-lived service with shallow rules usually pays the wiring cost without receiving much protection.<br />
<em><a href="Home/Software Architecture/Application Architecture/Clean Architecture.md" class="internal-link">Clean Architecture</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What is the difference between traditional layered and Onion/Clean Architecture?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Traditional layering points from UI to Business Logic to Data Access, so the business layer consumes the lower data API. Onion and Clean move the persistence contract inward and make Infrastructure implement it. Both separate responsibilities. Only the inward form prevents source dependencies from pulling infrastructure types into policy.<br />
<em><a href="Home/Software Architecture/Application Architecture/Layered Architecture.md" class="internal-link">Layered Architecture</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">How can plug-ins use different versions of the same dependency without breaking the host contract?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Each plug-in can load its private dependencies through its own <code>AssemblyLoadContext</code>. Plug-in A may then resolve <code>Newtonsoft.Json</code> 12.x while plug-in B resolves 13.x. The extension contract must still come from the host's default context. If a plug-in loads another copy of that contract assembly, its types have a different identity even when the name and source code match. Values should cross the boundary through the shared contract types and plain data.<br />
<em><a href="Home/Software Architecture/Application Architecture/Plug-in Architecture (MicroKernel).md" class="internal-link">Plug-in Architecture (MicroKernel)</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">When is plug-in architecture the wrong choice?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">It is the wrong choice when one team owns all features and releases them with the host. Dynamic loading and contract compatibility add failure modes without creating independent delivery. A modular monolith with feature flags handles that case with fewer moving parts. Plug-ins earn their cost when an extension must evolve without changing or rebuilding the core.<br />
<em><a href="Home/Software Architecture/Application Architecture/Plug-in Architecture (MicroKernel).md" class="internal-link">Plug-in Architecture (MicroKernel)</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What is the key difference between MVC and MVVM?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">MVC uses a controller to handle a request and select a response view. MVVM exposes observable state and commands to a long-lived bound view. MVC keeps a stateless request path explicit. MVVM accepts binding and notification machinery in exchange for persistent screen state without direct view manipulation.<br />
<em><a href="Home/Software Architecture/Application Architecture/Presentation Architecture Variants.md" class="internal-link">Presentation Architecture Variants</a></em></p>
</div></div></blockquote></span><h2 id="software-architecture-distributed-systems">Distributed Systems</h2><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">Why is 2PC problematic in microservices?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Prepared participants can hold locks while waiting for the coordinator's durable decision, so network faults reduce availability and throughput. Many common service boundaries do not support XA, which prevents them from joining the protocol.<br />
<em><a href="Home/Software Architecture/Distributed Systems/Distributed Transactions.md" class="internal-link">Distributed Transactions</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">How does the Outbox pattern support at-least-once event delivery?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">The message commits in the same local transaction as the domain change. A relay retries publication until acknowledged. A crash between broker acknowledgement and marking the row processed can publish twice, so consumers remain idempotent.<br />
<em><a href="Home/Software Architecture/Distributed Systems/Distributed Transactions.md" class="internal-link">Distributed Transactions</a></em></p>
</div></div></blockquote></span><h3>Message Queues</h3><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">How do Kafka and RabbitMQ fit different messaging workloads in a .NET service?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Kafka fits high-throughput event streams that must be retained and replayed. RabbitMQ fits low-latency work queues and messages that need flexible routing. For either broker, the design still needs a clear ordering boundary, such as a Kafka partition or a RabbitMQ queue, and the decision must include operating cost and the team's experience.<br />
<em><a href="Home/Software Architecture/Distributed Systems/Message Queues/Message Queues.md" class="internal-link">Message Queues</a></em></p>
</div></div></blockquote></span><h3>Scalability Patterns</h3><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What architectural prerequisites must be met before horizontal scaling works?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Work must be divisible, routing must reach an eligible owner, and state must have a sharing or partition-ownership rule. Stateless handlers satisfy those constraints by externalizing shared state. A <a class="internal-link" href="Home/Software Architecture/Distributed Systems/Load Balancing" aria-label="Home/Software Architecture/Distributed Systems/Load Balancing" data-tooltip-position="top">load balancer</a> can distribute requests, while stateful services also need replication, ownership, and failover coordination.<br />
<em><a href="Home/Software Architecture/Distributed Systems/Scalability Patterns/Horizontal Scaling.md" class="internal-link">Horizontal Scaling</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">Why can horizontal scaling fail even with many instances?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">More replicas can move saturation to the database, a connection pool, or an external quota. Local state can make replicas inconsistent, while sticky sessions or hot keys create uneven load. Startup delay also means new replicas may arrive after the overload has already caused failures.<br />
<em><a href="Home/Software Architecture/Distributed Systems/Scalability Patterns/Horizontal Scaling.md" class="internal-link">Horizontal Scaling</a></em></p>
</div></div></blockquote></span><h2 id="software-architecture-patterns">Patterns</h2><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">Why does CQS make code easier to reason about?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">The contract separates observation from mutation. Queries can be repeated or cached only when their no-side-effect promise holds. Commands expose the paths that need authorization, transaction boundaries, and retry analysis. The distinction reduces the amount of implementation detail required to judge a call site.<br />
<em><a href="Home/Software Architecture/Patterns/CQS.md" class="internal-link">CQS</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">When is it pragmatic to violate CQS?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">A combined operation is justified when separation breaks a coherent transition or adds a wasteful round trip. <code>Stack.Pop()</code> is the classic single-threaded shape; <code>ConcurrentStack&lt;T&gt;.TryPop()</code> supplies the atomic concurrent form. A create command returning its generated identifier is another. The exception should keep mutation, retry safety, and returned data explicit.<br />
<em><a href="Home/Software Architecture/Patterns/CQS.md" class="internal-link">CQS</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">Explain <code>Transient</code>, <code>Scoped</code>, and <code>Singleton</code> lifetimes with a safe production example each.</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">The lifetime controls how long the container reuses an instance:</p>
<ul>
<li dir="auto"><strong>Transient:</strong> one instance per resolution, suitable for a lightweight stateless mapper.</li>
<li dir="auto"><strong>Scoped:</strong> one instance per scope. In ASP.NET Core, a scoped <code>DbContext</code> gives one request a coherent unit of work.</li>
<li dir="auto"><strong>Singleton:</strong> one instance for the application lifetime, suitable for a thread-safe cache or <code>IClock</code>.<br />
Lifetime is a shared-state decision, not a performance setting. A singleton cannot safely capture a scoped service.<br />
<em><a href="Home/Software Architecture/Patterns/Dependency Injection.md" class="internal-link">Dependency Injection</a></em></li>
</ul>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What is a captive dependency, and how can it be fixed?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">A captive dependency appears when a longer-lived service stores a shorter-lived one, classically an <code>IHostedService</code> holding a scoped <code>DbContext</code>. The scoped object escapes its boundary, so request state may leak across work and disposal happens too late. Scope validation catches this configuration when enabled. The repair is to inject <code>IServiceScopeFactory</code>, create a short scope for the operation, resolve the scoped service inside it, and dispose the scope when the operation ends.<br />
<em><a href="Home/Software Architecture/Patterns/Dependency Injection.md" class="internal-link">Dependency Injection</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What evidence justifies introducing a pattern?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">A recurring variation, responsibility boundary, or failure mode must be visible in the code. The pattern should make that pressure cheaper to handle than the direct design. Without that evidence, the extra indirection is speculative complexity.<br />
<em><a href="Home/Software Architecture/Patterns/Patterns.md" class="internal-link">Patterns</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">Why does EF Core's DbContext already implement the Unit of Work pattern?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto"><code>DbContext</code> tracks entity changes and sends the pending work through <code>SaveChangesAsync()</code>, which uses a transaction when the provider supports it. Several repositories participate in one unit only when they share the same context instance. A singleton context is unsafe, while separate transient contexts split the commit boundary.<br />
<em><a href="Home/Software Architecture/Patterns/Repository &amp; UoW.md" class="internal-link">Repository &amp; UoW</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">When is a generic <code>IRepository&lt;T&gt;</code> an anti-pattern?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">It becomes an anti-pattern when the generic CRUD surface replaces aggregate-specific access rules. <code>GetAll()</code> may be meaningless for a large aggregate, and unrestricted updates can bypass invariants. A generic implementation can remain inside infrastructure. The domain-facing interface should describe the operations the aggregate actually supports.<br />
<em><a href="Home/Software Architecture/Patterns/Repository &amp; UoW.md" class="internal-link">Repository &amp; UoW</a></em></p>
</div></div></blockquote></span><h3>Architectural Patterns</h3><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">When is CQRS useful, and when does it add unnecessary complexity?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">CQRS is useful when the write side and the read side have clearly different needs. For example, writes may enforce order and payment rules, while reads need data prepared for fast searches and reports.</p>
<p dir="auto">It is not useful when the same model already handles both sides without difficulty. In that case, maintaining a separate read model and keeping it synchronized adds complexity without enough benefit.<br />
<em><a href="Home/Software Architecture/Patterns/Architectural Patterns/CQRS.md" class="internal-link">CQRS</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">When is full DDD the wrong choice?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">A system with straightforward CRUD and little business behavior gains little from aggregates, repositories, and context mapping. Strategic boundaries may still help a large organization, but tactical machinery should follow real invariants rather than project size alone.<br />
<em><a href="Home/Software Architecture/Patterns/Architectural Patterns/Domain-Driven Design.md" class="internal-link">Domain-Driven Design</a></em></p>
</div></div></blockquote></span><h3>Design Patterns</h3><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">How is a GoF category chosen?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Creational patterns vary how objects come into existence. Structural patterns vary how types or objects are assembled. Behavioral patterns vary responsibility and communication. The category is a recall aid. The pattern's intent still decides whether it fits.<br />
<em><a href="Home/Software Architecture/Patterns/Design Patterns/Design Patterns.md" class="internal-link">Design Patterns</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">When does using a design pattern become an anti-pattern?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">When its indirection costs more than the variation it isolates. A Factory Method with one permanent product, a Builder around two independent values, or a Singleton hiding request state adds vocabulary without removing design pressure. Concrete evidence of variation should pay for the abstraction.<br />
<em><a href="Home/Software Architecture/Patterns/Design Patterns/Design Patterns.md" class="internal-link">Design Patterns</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">How can two patterns with the same wrapper shape be distinguished?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Name the responsibility that the wrapper owns. A Decorator adds behavior, a Proxy controls access, and an Adapter translates a contract. Class shape alone cannot identify the pattern because intent and collaboration are part of its definition.<br />
<em><a href="Home/Software Architecture/Patterns/Design Patterns/Design Patterns.md" class="internal-link">Design Patterns</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">How does Information Expert reduce coupling, and when should another principle override it?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">It places behavior beside the information it needs, so another object does not have to pull data out and reproduce the rule. Low Coupling or Pure Fabrication should override it when that placement would import infrastructure, coordinate other aggregates, or give the object unrelated responsibilities.<br />
<em><a href="Home/Software Architecture/Patterns/Design Patterns/GRASP.md" class="internal-link">GRASP</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">How does GRASP differ from SOLID?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">GRASP focuses on assigning responsibilities among collaborating objects. SOLID describes broader properties of class and dependency design. They overlap around cohesion, coupling, and variation, but GRASP starts with ownership: who should do the work?<br />
<em><a href="Home/Software Architecture/Patterns/Design Patterns/GRASP.md" class="internal-link">GRASP</a></em></p>
</div></div></blockquote></span><h4>Behavioral</h4><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">How does ASP.NET Core Middleware differ from a classical Chain of Responsibility?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Classical CoR usually links handler objects directly. ASP.NET Core composes middleware delegates into one request pipeline at startup. That pipeline is fixed after the application is built, while a conventional object chain may be rearranged at runtime. The practical boundary is startup composition versus runtime mutation.<br />
<em><a href="Home/Software Architecture/Patterns/Design Patterns/Behavioral/Chain of Responsibility.md" class="internal-link">Chain of Responsibility</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">How does MediatR implement the Command pattern, and what does it add?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto"><code>PlaceOrderCommand</code> carries the request, while <code>PlaceOrderCommandHandler</code> owns execution. MediatR routes between them and can wrap handlers with pipeline behaviors. That indirection is useful when dispatch and shared policies matter across many requests. A direct service call remains clearer for a small, fixed interaction.<br />
<em><a href="Home/Software Architecture/Patterns/Design Patterns/Behavioral/Command.md" class="internal-link">Command</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What should determine whether an API returns <code>IEnumerable&lt;T&gt;</code>, <code>IReadOnlyList&lt;T&gt;</code>, or <code>IAsyncEnumerable&lt;T&gt;</code>?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">The return type should describe what the caller can safely rely on. <code>IReadOnlyList&lt;T&gt;</code> guarantees <code>Count</code> and indexed access, but it does not say whether values are computed lazily or represent a snapshot. If the method returns a materialized snapshot, that should be stated separately in the method's contract. <code>IEnumerable&lt;T&gt;</code> promises only synchronous enumeration, which may be lazy and repeat the underlying work when enumerated again. <code>IAsyncEnumerable&lt;T&gt;</code> fits a source that waits between items and should stream them instead of buffering the full result.<br />
<em><a href="Home/Software Architecture/Patterns/Design Patterns/Behavioral/Iterator.md" class="internal-link">Iterator</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What does the compiler generate for a <code>yield return</code> method?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">The compiler generates a state-machine type that implements the enumeration contracts. Each <code>yield return</code> becomes a suspension point. <code>MoveNext()</code> resumes execution and <code>Current</code> exposes the yielded value. Locals that must survive suspension become fields on the generated object.<br />
<em><a href="Home/Software Architecture/Patterns/Design Patterns/Behavioral/Iterator.md" class="internal-link">Iterator</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What are the signs that a mediator is adding indirection without reducing coupling?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">A mediator should route work, not become the place where business rules accumulate. Moving a 300-line workflow from a controller into one handler changes its location without reducing its complexity or dependencies. For a simple, stable interaction, a direct dependency is usually clearer.<br />
<em><a href="Home/Software Architecture/Patterns/Design Patterns/Behavioral/Mediator.md" class="internal-link">Mediator</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">How do MediatR pipeline behaviors implement the Chain of Responsibility pattern?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">

<p dir="auto">A full snapshot is wasteful when undo can be represented as one small delta. If restoring a removed item needs only that item and its position, store those values. Memento earns the extra copy when state is interdependent or restoration must survive across sessions.<br />

<p dir="auto">A delegate is enough when the variation is one operation and its inputs contain everything it needs. </div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">When does payment-provider selection need Bridge rather than Strategy?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Strategy swaps one behavior behind an interface. Bridge connects two independently changing models. Provider selection alone needs Strategy. Provider selection combined with a growing set of payment operations may justify Bridge.<br />
<em><a href="Home/Software Architecture/Patterns/Design Patterns/Structural/Bridge.md" class="internal-link">Bridge</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What makes the payment example Bridge rather than ordinary provider polymorphism?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Both sides vary. <code>PaymentOperation</code> has charge, subscription, or refund variants, while <code>IPaymentGateway</code> has Stripe, PayPal, or bank implementations. Provider implementations can grow independently, and operation variants can grow independently while they compose existing gateway primitives. A new primitive still changes the gateway contract and every provider. Injecting only one gateway behind one service interface would be ordinary polymorphism or Strategy.<br />
<em><a href="Home/Software Architecture/Patterns/Design Patterns/Structural/Bridge.md" class="internal-link">Bridge</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">How does Bridge differ from dependency injection?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Dependency injection supplies an object with its dependencies. Bridge is the design decision to keep an abstraction and its implementation as separate models that can vary independently and connect through composition. DI can wire an <code>IPaymentGateway</code> into a <code>PaymentOperation</code>, but that wiring does not create the two dimensions or prove that they need to evolve separately.<br />
<em><a href="Home/Software Architecture/Patterns/Design Patterns/Structural/Bridge.md" class="internal-link">Bridge</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">How does Composite relate to the Visitor pattern?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Composite gives leaves and groups one interface, and each group can recurse through its children. Visitor adds an operation across the node types without putting that operation on every node. They work well together when the tree structure belongs to Composite, the set of node types is stable, and operations change more often than the nodes.<br />
<em><a href="Home/Software Architecture/Patterns/Design Patterns/Structural/Composite.md" class="internal-link">Composite</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">When does a Composite tree become a performance problem?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Cost grows with the number of visited nodes. A bundle containing 10,000 SKUs makes <code>GetPrice()</code> visit those nodes on each uncached call. Profiling should decide whether to cache totals or update an aggregate during mutation. Either choice introduces an invalidation rule.<br />
<em><a href="Home/Software Architecture/Patterns/Design Patterns/Structural/Composite.md" class="internal-link">Composite</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">How does ASP.NET Core Middleware implement the Decorator pattern?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Each middleware receives a <code>RequestDelegate</code> for the remaining pipeline. It can run logic before delegation, after delegation, or stop the chain. Startup composition fixes the wrapper order, so ordering mistakes appear as runtime behavior rather than type errors.<br />
<em><a href="Home/Software Architecture/Patterns/Design Patterns/Structural/Decorator.md" class="internal-link">Decorator</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">When should Decorator replace inheritance for added behavior?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Decorator suits optional behavior assembled at composition time, especially around sealed or third-party types. Inheritance suits a stable subtype relationship. A decorator avoids coupling behavior to a base-class implementation, but introduces another object and call boundary.<br />
<em><a href="Home/Software Architecture/Patterns/Design Patterns/Structural/Decorator.md" class="internal-link">Decorator</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What's the performance cost of a deep decorator chain?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Each decorator adds a call boundary and may add asynchronous state-machine work if its method awaits. I/O usually dominates that cost. A CPU-bound hot path still deserves measurement. If wrapper overhead appears in profiles, collapsing layers on that path may be reasonable.<br />
<em><a href="Home/Software Architecture/Patterns/Design Patterns/Structural/Decorator.md" class="internal-link">Decorator</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">When does a Facade become a "god class" anti-pattern?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">The shift happens when orchestration becomes ownership of business rules or mutable domain state. <code>OrderFacade</code> may call pricing and validation services in sequence. It should not become the place where those rules are implemented. Difficulty testing the facade without reproducing the whole domain is a stronger signal than a line-count threshold.<br />
<em><a href="Home/Software Architecture/Patterns/Design Patterns/Structural/Facade.md" class="internal-link">Facade</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">When is Flyweight not worth the complexity?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">It is not worth using when duplicate state is a small part of the process heap or object counts stay low. A memory profiler should show many equal, retained objects before the model is split. The factory and lookup path otherwise add complexity without relieving a measured constraint.<br />
<em><a href="Home/Software Architecture/Patterns/Design Patterns/Structural/Flyweight.md" class="internal-link">Flyweight</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What's the difference between a Proxy and a Decorator in terms of intent?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">A proxy stands in for the subject to control access to it. A decorator attaches another responsibility while preserving the component contract. Their class diagrams can look identical, so the design intent and the wrapper's reason for existing settle the classification.<br />
<em><a href="Home/Software Architecture/Patterns/Design Patterns/Structural/Proxy.md" class="internal-link">Proxy</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">Decorator and Proxy can have the same class structure. What determines which pattern is present?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Intent. A Decorator adds composable behavior to an object. A Proxy controls access to another object, perhaps by deferring creation or enforcing authorization. The wrapper's responsibility and the reason it exists matter more than the diagram.<br />
<em><a href="Home/Software Architecture/Patterns/Design Patterns/Structural/Structural.md" class="internal-link">Structural</a></em></p>
</div></div></blockquote></span><h2 id="software-architecture-system-architecture">System Architecture</h2><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">Why do microservices create distributed data consistency problems, and what keeps a cross-service workflow reliable?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">Each service commits its own data, so a cross-service workflow cannot rely on one local ACID transaction. One service may commit successfully and a later step may fail. The workflow is usually split into local transactions connected by a saga. Outbox and inbox patterns make message transfer recoverable, and idempotent handlers make redelivery safe.</p>
<p dir="auto">If a completed step must be reversed, the saga runs a business compensation where that is possible. Its state must remain visible so the system can keep retrying, finish later, or wait for manual repair instead of leaving partial work hidden.<br />
<em><a href="Home/Software Architecture/System Architecture/Microservices.md" class="internal-link">Microservices</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What architecture usually fits a new product, and what evidence would justify moving to microservices?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">The starting point is the release and ownership constraint, not a preferred topology. One team still discovering the domain usually gets the fastest feedback from a monolith. A modular monolith keeps changes and transactions in-process while enforcing domain boundaries.</p>
<p dir="auto">Microservices become justified when a stable boundary repeatedly needs independent deployment or scaling, and the team can own the added operational cost. Until that pressure is measured, distribution adds network and data-consistency problems without buying real independence.<br />
<em><a href="Home/Software Architecture/System Architecture/Microservices.md" class="internal-link">Microservices</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What evidence shows that an extracted service is independent rather than part of a distributed monolith?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<ul>
<li dir="auto">Its team can change, deploy, roll back, and operate it without a paired release.</li>
<li dir="auto">It owns its writable data and exposes a versioned contract. Dependency failure behavior is defined and exercised.</li>
<li dir="auto">Traces and reconciliation prove that synchronous calls and later messages can be followed across the boundary.<br />
<em><a href="Home/Software Architecture/System Architecture/Microservices.md" class="internal-link">Microservices</a></em></li>
</ul>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">When is a modular monolith a better fit than microservices, and what signals justify extracting a module?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">A modular monolith fits while business domains stay cleanly separated into modules and one deployment remains reliable. Extraction becomes worthwhile when one module repeatedly needs its own scaling, release cadence, or isolation policy. The domain contract can remain familiar, but the remote interaction must be redesigned around deadlines, retries, observability, and local transactions.<br />
<em><a href="Home/Software Architecture/System Architecture/Modular Monolith.md" class="internal-link">Modular Monolith</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What evidence justifies extracting a service?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">A stable boundary should already exist, and the module should repeatedly need an independent release cadence, runtime isolation, or scaling profile. Extraction without those pressures usually trades visible code coupling for harder operational coupling.<br />
<em><a href="Home/Software Architecture/System Architecture/Monolith Architecture.md" class="internal-link">Monolith Architecture</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">Which part of SOA remains useful without SOAP, WSDL, or an ESB?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">The durable part is the explicit service contract around a business capability. Consumers depend on that contract instead of importing the service's internal code or writing directly to its database. This allows systems built on different technology stacks to change independently as long as the contract stays compatible. SOAP, WSDL, and ESBs were common ways to implement or govern that boundary, but the boundary still matters when the transport is HTTP, gRPC, or messaging.<br />
<em><a href="Home/Software Architecture/System Architecture/Service-Oriented Architecture.md" class="internal-link">Service-Oriented Architecture</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What determines whether an event-driven workflow uses orchestration or choreography?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">The main question is whether one component must own the process from start to finish. An ordered checkout with compensation steps fits <a class="internal-link" href="Home/Software Architecture/Distributed Systems/Orchestration" aria-label="Home/Software Architecture/Distributed Systems/Orchestration" data-tooltip-position="top">orchestration</a> because the current step and recovery state need one visible owner. Independent reactions to <code>OrderPlaced</code>, such as email, analytics, or indexing, fit <a class="internal-link" href="Home/Software Architecture/Distributed Systems/Choreography" aria-label="Home/Software Architecture/Distributed Systems/Choreography" data-tooltip-position="top">choreography</a> because no subscriber controls the others. Asynchronous messaging supports both styles; it does not force choreography.<br />
<em><a href="Home/Software Architecture/System Architecture/Event-Driven Architecture.md" class="internal-link">Event-Driven Architecture</a></em></p>
</div></div></blockquote></span><h1 id="software-design">Software Design</h1><h2 id="software-design-paradigms">Paradigms</h2><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What makes a function "pure" and why does purity matter for testing?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">For inputs in its defined domain, its observable result depends only on explicit inputs, and evaluating it does not change external state. Tests therefore pass values and assert values instead of arranging clocks, databases, or global configuration. A throwing input makes the function partial rather than supplying a substitutable result; expected invalid inputs can be modeled as returned values when totality matters. Real systems keep I/O and external state in a surrounding shell and pass their results into the pure core.<br />
<em><a href="Home/Software Design/Paradigms/Functional Programming.md" class="internal-link">Functional Programming</a></em></p>
</div></div></blockquote></span><h2 id="software-design-testing">Testing</h2><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">How can TDD improve design beyond increasing test coverage?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">The test is the first concrete caller, so construction, inputs, outputs, and failure semantics must be expressed before implementation details dominate. Difficult setup is a design signal worth investigating, not proof that a class must be split. The benefit comes from selecting the next useful example and refactoring after it passes. A test that begins green may document existing behavior, but it does not prove that the intended production change was necessary.<br />
<em><a href="Home/Software Design/Testing/Test-Driven Development.md" class="internal-link">Test-Driven Development</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">When is TDD not worth the overhead?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">The loop has little leverage when the work is a disposable experiment, a mechanical declaration already guaranteed by a framework, or a visual exploration whose useful feedback comes from rendering rather than a code-level example. That does not remove the need for verification before the behavior becomes durable. There is no universal percentage cost: the tradeoff depends on domain familiarity, test level, tooling, and how much change the code will absorb.<br />
<em><a href="Home/Software Design/Testing/Test-Driven Development.md" class="internal-link">Test-Driven Development</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">What is the difference between a stub and a mock?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">A stub supplies answers needed to reach the behavior. A mock is configured with interaction expectations and verifies them. A spy records calls for later assertions, while a fake provides a working simplified implementation. Frameworks often let one object play several roles, so the distinction is about how the test uses the double. Prefer result assertions when they expose the behavior, and interaction assertions when the command itself is the observable contract.<br />
<em><a href="Home/Software Design/Testing/Unit Testing.md" class="internal-link">Unit Testing</a></em></p>
</div></div></blockquote></span><span><blockquote class="callout is-collapsible is-collapsed node-insert-event" data-callout="question" data-callout-fold="" data-callout-metadata=""><div dir="auto" class="callout-title"><div class="callout-icon"><svg xmlns="http://www.w3.org/2000/svg" height="16" width="16"/></div><div class="callout-title-inner">When is a unit test the wrong testing layer?</div><div class="fold-callout-icon is-collapsed"></div></div><div style="display: none;" class="callout-content"><div class="callout-content-inner">
<p dir="auto">A unit test adds little value when it only repeats language or framework behavior, such as an uncustomized property accessor. Failures in visual rendering, dependency registration, configuration binding, or database-provider behavior need a component or integration test that can observe that boundary. Exploratory code may start without tests, but behavior kept in production still needs evidence that matches its risk. The best layer is the cheapest one that can catch the realistic failure.<br />
<em><a href="Home/Software Design/Testing/Unit Testing.md" class="internal-link">Unit Testing</a></em></p>
</div></div></blockquote></span></div>
