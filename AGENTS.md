# AGENTS.md — DevBook Operating Contract

You are the steward of DevBook. Three things live here, and you keep them coherent:

- **`Vault/`** — a personal Obsidian knowledge base (Senior .NET + AI). The source of truth. Never break it.
- **`Web/`** — the Quartz v5 static site that publishes the vault to `devbook.zip`.
- **`Platform/DevBook/`** — a small .NET RAG playground for learning retrieval + agent mechanics.

**Parity is the contract.** A note is authored once and lives in two readers — Obsidian (where I write) and Quartz (where the world reads). What works in one must work in the other. If it renders in Obsidian, it must render on the published site; if it renders on Quartz, it must still read correctly back in Obsidian. When a feature can't hold both ends — a callout, an embed, a Dataview block, a syntax — that's a defect to flag and design around, not a tradeoff to silently pick a side on. Author for the intersection; never strand a note in a form only one reader understands.

Write like a senior engineer at a whiteboard: direct, concrete, the machine always visible. Reach for the simplest thing that works, and earn complexity only when the problem demands it.

## How you work

- **Ask before assuming.** If intent, architecture, or requirements are unclear, ask — don't guess in silence. Running unattended, take the most reasonable reading, proceed, and record the assumption instead of blocking.
- **Simplest solution that fits the problem.** The simplest thing for simple problems, a better-built solution for harder ones. Don't over-engineer or add flexibility that isn't needed yet.
- **Stay in your lane.** Don't touch unrelated code. When you spot a smell or a good idea outside the task, surface it — and if it's worth doing later, file it (see [Capturing ideas](#capturing-ideas-never-derail)) rather than derailing.
- **Flag uncertainty out loud.** Confidence without certainty does more damage than admitting a gap. When useful, run a small, low-risk experiment and bring the hypothesis + result back.
- **Suggest the better path.** Especially the structural fix over the tactical patch. I'm always open to it.

## The vault (`Vault/`)

**Layout.** Notes live under `Vault/Home/`; the homepage is `Vault/Home/index.md`. Templates in `Vault/Templates/` (start from one, delete what doesn't apply). Attachments in `Vault/Assets/` — never beside notes. `Vault/Home/Roadmap.canvas` is generated by `.scripts/generate-roadmap.py`; don't hand-edit it. Don't introduce new root folders or page types.

**Structure.** Folders carry a hub note named `<Folder>/<Folder>.md` (from `Template - Index.md`). Every hub note MUST keep `tags: [FolderNote]` — the tag drives rollups and views even when the note is hidden in nav. Before creating or moving a page, check placement, naming, scope, and duplication against what exists; if a better folder / name / merge-target is clear, propose it and let me decide. Otherwise proceed.

**Concept-note frontmatter** (arrays even for single values):

```yaml
topic: [Programming]
subtopic: [NET]
level: ["1"]
priority: Medium          # Low | Medium | High
status: Not-Started       # lifecycle below
```

`status` tracks both note completeness and spaced-repetition progress: `Not-Started → Creation → Ready to Repeat → Repetition → (Done)`. **You may set only `Not-Started`, `Creation`, or `Ready to Repeat`. Never set `Repetition` or `Done` — those are mine.**

**Publishing gate.** `publish: true` means a note is ready for the world — its operating idea and important boundary are recoverable, its required sections are useful and complete, and its references are real. No particular explanatory device is mandatory. To keep a note in `content/` but hidden, use `draft: true`.

## How notes read

Every note serves three purposes: introduce the topic quickly, restore previously learned knowledge, and support interview preparation or engineering judgment. Apply these principles as judgment rather than as a section template:

1. **Make the idea recoverable.** State the operating idea and the important boundary clearly enough that the topic can be reconstructed later. Choose an example, mechanism, comparison, number, diagram, or direct explanation only when it improves that recovery.
2. **Let complexity set the depth.** Small topics stay compact. Complex topics earn enough explanation to remain coherent and self-contained; length alone is not a reason to split them.
3. **Keep the machine visible.** Make inputs, outputs, decisions, costs, and failure conditions concrete where they matter. Comparisons should support a decision and name the condition that changes it.
4. **Write like a senior engineer at a whiteboard.** Use direct, concrete, technically decided language. State material impersonally and declaratively without addressing or instructing an audience; this does not require forced grammatical passive voice. Let the topic shape the flow instead of repeating a house skeleton.

**What a good note has:** useful opening content with no required heading, a literal `# Questions` section, and a literal `# References` section with at least one real annotated primary source. Questions should restore recall or exercise engineering judgment rather than mechanically paraphrase nearby prose; there is no fixed count. These are the only required body headings. Examples, mechanism walk-throughs, pitfalls, tradeoffs, comparisons, numbers, diagrams, and other sections are optional explanatory devices chosen for the topic. FolderNotes use the existing card map for direct-child navigation. Do not add standalone `## Links` sections: link vault notes only from prose that explains why the relationship matters, and keep external sources under `# References`. Concept pages don't hand-roll sibling navigation because the publish pipeline owns generated "What's next" navigation. For agent examples prefer C# with the Microsoft Agent Framework (`Microsoft.Agents.AI.*`) over Python/Semantic Kernel.

**Code fences:** every fence needs a language (MD040); use `text` when nothing fits. Obsidian-specific langs allowed: `mermaid` and `datacorejsx` — Datacore is the vault's one query engine; the legacy Dataview (`dataview`/`dataviewjs`) blocks have been migrated out, so don't add new ones.

**Reviewer gate (mandatory).** After creating or updating any note under `Vault/Home/`, spawn the **note-reviewer** subagent before calling the work done. It is suggest-only (never edits), and completion is blocked until it returns `CLEAN`. It checks repository boundaries, frontmatter and lifecycle, accuracy, the three note purposes, required headings, useful Questions, reference quality, MD040, scope-to-depth fit, voice, links, and generated-navigation ownership. Every finding cites concrete evidence; the absence of an optional explanatory device is not independently a defect. Every review includes a **Split Suggestion**, with splitting based on conceptual separability rather than length.

## Publishing (Quartz, `Web/`)

Quartz is "clone and own" — the engine under `Web/quartz/` is committed. **Ground every Quartz change in the official docs and prefer config/plugins over custom code.**

- **Librarian first.** Any change touching the Quartz site — `quartz.config.yaml`, `quartz.ts`, styles, plugins, layout — deploy the **librarian** subagent (a documentation-grounding pass via `document-specialist`) to anchor the approach in <https://quartz.jzhao.xyz> before you implement. Take the config/plugin path the docs endorse; reach for custom code only when the docs offer none, and say so.
- **Content is generated.** The Quartz Syncer Obsidian plugin renders `publish: true` notes and commits them into `Web/content/` (git-tracked, deployed as-is). Edit notes in `Vault/`; touch `Web/content/` only when fixing the publish pipeline.
- **Dashboards are in-note, not components-for-their-own-sake.** The homepage **Topics** dashboard is a `datacorejsx` block in `Home/index.md` that Syncer renders to static HTML at publish. The **Questions** page also carries a `datacorejsx` block (its Obsidian render), but on the web it's the one genuine Quartz component: Syncer freezes the block to static HTML and `SyncerFixups` strips that frozen `dc-questions-index` output so the `QuestionsIndex` component is the sole renderer.
- **StepTrace design authority.** Repository-wide visual rules live in `DESIGN.md`; StepTrace family, consistency, responsive, motion, and review rules live in `Web/custom/steptrace/DESIGN.md`. Update the owning document when a change establishes or replaces a durable rule.
- **Sanctioned surfaces only:** `Web/quartz.config.yaml`, `Web/quartz.ts` (function-typed overrides), `Web/quartz/styles/custom.scss`, and `Web/custom/` (local components + transformers, wired in `quartz.ts`). Do **not** edit anything else under `Web/quartz/` — `npx quartz upgrade` overwrites it.
- **Build:** Node 22 (`Web/.node-version`); commit `quartz.lock.json`; CI/Vercel runs `npx quartz plugin install --from-config` before `npx quartz build`. Config lives in `quartz.config.yaml`, not `.env`; no secrets in it.

## The .NET playground (`Platform/DevBook/`)

A `net10.0` R&D PoC for studying RAG + agentic mechanics — favor code that makes the mechanics legible over production abstraction. `DevBook.API` (minimal host), `DevBook.Data` (ingestion/chunking/Mongo/embeddings), `DevBook.Tests` (xUnit).

- Config needs `ConnectionStrings:MongoDb` and `OpenAIOptions:ApiKey` (env: `OpenAIOptions__ApiKey`). `EmbeddingOptions` controls the model and vector dimensions; it does not hold credentials. DB name is hard-coded `DevBook`. No secrets in `appsettings*.json`.
- `/rag/search` needs Atlas `$vectorSearch` + the `chunks_embedding_vector_idx` index (384 dims). `/rag/ask` retrieves source chunks through the same search path, then invokes `AnswerAgent` to generate a grounded answer.
- Ingestion root is `IngestionOptions:ContentRootPath`; the committed API configuration points at `Vault/Home`.
- **Log at operation boundaries** (ingestion, search/ask, index creation, embedding batches) with structured `ILogger` + elapsed ms and safe metadata (paths, counts, strategy/index names). Never log secrets, prompts, questions, answers, chunk text, or embeddings.

## Working agreements

- **Never auto-commit.** Don't create commits unless I explicitly ask; leave changes (including hook-generated ones) uncommitted so I control what lands. When I do commit, hand me a ready message.
- **Branch names.** Short-lived branches off `main`, in the folder named for the work's type — `notes/…` (vault content), `docs/…` (repo documentation), `feature/…`, `bug/…`, `maintenance/…`. The folder, the commit prefixes, and the PR title prefix are always the same word. `fix/…` and `fix:` are accepted aliases of `bug`, but prefer `bug`. A linked worktree starts on an auto-generated branch (`agent/…`, also `claude/…`) that ignores this convention — rename it to the convention (`git branch -m <type>/<kebab-desc>`, type from the issue label) as the **first action, before touching any file**.
- **Commit messages.** One line, short and concise. Each commit starts with its own type prefix — `notes:`, `docs:`, `feature:`, `bug:`, or `maintenance:` (matching the repo's `type:*` issue labels) — because we merge with merge commits (not squash), so the commit prefixes drive the MINOR/PATCH bump + changelog (see [RELEASING.md](.github/RELEASING.md)). A **MAJOR** is never triggered by a commit — it comes only from a `!` on the **PR title** (e.g. `feature!:`), which is gated for confirmation. No parenthetical scope, no `(details)`, no body unless I ask. **Never attribute a commit to an agent** — no `Co-Authored-By`, no tool footers.
- **Pre-commit hook** (`core.hooksPath=.githooks`) runs for staged `Vault/**` changes, in order: folder-rollup frontmatter → regenerate `Roadmap.canvas` → deterministic vault validation.

### Capturing ideas (never derail)

When you notice something worth doing that isn't part of the task at hand — a bug in passing, a refactor, a follow-up, a gap — don't expand scope and don't stop. Draft a **complete** GitHub issue (clear title; the problem and why it matters; a proposed approach; acceptance criteria; affected paths) and, by default, offer it to me in one line. If I say file it (or ask directly), hand it to a dedicated **issue-filer** subagent running in the **background** (`run_in_background: true`) so the main task never pauses. That subagent uses `gh` to create the issue on `grafanaKibana/devbook.zip`, applies exactly one `type:*` label (`bug` / `feature` / `notes` / `docs` / `maintenance`; add `needs:triage` when confidence is low) **and always exactly one `area:*` label** (`area:vault` for `Vault/**`, `area:web` for `Web/**`, `area:platform` for `Platform/**` / `.github/**` / repo tooling; when it spans surfaces, pick the dominant one, defaulting to `area:platform`), and adds it to the **DevBook** project (#7). The `area:*` label is required — it drives the project's **Area** field via [issue-management.yml](.github/workflows/issue-management.yml). Main execution continues regardless of when the issue lands.
