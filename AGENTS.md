# AGENTS.md — DevBook Operating Contract

DevBook contains the Obsidian source vault (`Vault/`), its Quartz site (`Web/`), and a small .NET RAG playground (`Platform/DevBook/`). Author notes once in `Vault/`; preserve their meaning and supported rendering in both Obsidian and Quartz. Flag a reader mismatch rather than silently accepting it.

## Working agreements

- Keep changes scoped and preserve unrelated local work. Choose the simplest sound solution, verify assumptions, and report uncertainty. Ask when missing intent materially changes the work; unattended runs may proceed with a recorded reasonable assumption.
- Never create commits unless explicitly requested. Keep commit messages short, one line, without scopes, bodies, agent attribution or tool footers. Never auto-merge.
- Use `notes/`, `docs/`, `feature/`, `bug/` or `maintenance/` branches with the same prefix on commits and PR titles; `fix` is a supported alias of `bug`. Rename an automatically generated `agent/` or `claude/` branch before editing. Follow [release conventions](.github/RELEASING.md).
- Verify changed behavior with focused checks. Protect data integrity, destructive-operation guards and Obsidian/Quartz parity; avoid redundant private-implementation tests and snapshots. Tooling uses [DevBook.Tooling.slnx](.scripts/DevBook.Tooling.slnx), PascalCase C# filenames, and xUnit/FluentAssertions tests with Arrange/Act/Assert groups. The RAG solution has its own tests.
- Keep follow-ups out of the current task. Offer a complete issue draft; file only when asked, using the issue-filer subagent. Filed issues need one `type:*`, one `area:*` label and the DevBook project (#7); use `area:platform` for repository tooling or mixed scope, and `needs:triage` when uncertain.
- Change these rules only when explicitly requested. Keep setup, implementation details and recovery procedures in their owning documents instead of appending task history here.

## The vault (`Vault/`)

**Layout.** Notes live under `Vault/Home/`; the homepage is `Vault/Home/index.md`. Templates in `Vault/Templates/` (start from one, delete what doesn't apply). Attachments in `Vault/Assets/` — never beside notes. `Vault/Home/Roadmap.canvas` is generated by `.scripts/DevBook.Tooling/Scripts/GenerateRoadmap.cs`; don't hand-edit it. Don't introduce new root folders or page types.

**Structure.** Folders carry a hub note named `<Folder>/<Folder>.md` (from `Template - Index.md`). Every hub note MUST keep `tags: [FolderNote]` — the tag drives rollups and views even when the note is hidden in nav. Before creating or moving a page, check placement, naming, scope, and duplication against what exists; if a better folder / name / merge-target is clear, propose it and let me decide. Otherwise proceed.

**Concept-note frontmatter** (arrays even for single values):

```yaml
topic: [Programming]
subtopic: [NET]
level: ["1"]
priority: Medium          # Low | Medium | High
status: Not-Started       # lifecycle below
```

`status` tracks both note completeness and spaced-repetition progress: `Not-Started → Creation → Ready to Repeat → Repetition → (Done)`. **You may set only `Not-Started`, `Creation`, or `Ready to Repeat`. Never set `Repetition` or `Done` — those are mine.**

**Publishing gate.** `publish: true` means a note is ready for the world — its operating idea and important boundary are recoverable, and any included supporting sections are useful and complete. No particular explanatory device, Questions section, or References section is mandatory. To keep a note in `content/` but hidden, use `draft: true`.

## How notes read

Every concept or folder note serves three purposes: introduce the topic quickly, restore previously learned knowledge, and support interview preparation or engineering judgment. Apply these principles as judgment rather than as a section template:

1. **Make the idea recoverable.** State the operating idea and the important boundary clearly enough that the topic can be reconstructed later. Choose an example, mechanism, comparison, number, diagram, or direct explanation only when it improves that recovery. These principles are thinking prompts, not a vocabulary template; name the concrete mechanism, decision, failure, or limit instead of echoing the rubric.
2. **Let complexity set the depth.** Small topics stay compact. Complex topics earn enough explanation to remain coherent and self-contained; length alone is not a reason to split them. Compact means no wasted prose, not less explanation; preserve the technical detail the topic depends on.
3. **Keep the machine visible.** Make inputs, outputs, decisions, costs, and failure conditions concrete where they matter. Comparisons should support a decision and name the condition that changes it.
4. **Write like a senior engineer at a whiteboard.** Use direct, concrete, technically decided language. State material impersonally and declaratively without addressing or instructing an audience; this does not require forced grammatical passive voice. Let the topic shape the flow instead of repeating a house skeleton.

**What a good concept or folder note has:** useful opening content with no required heading and no mandatory body sections. `# Questions` and `# References` are optional; add either only when it contains useful content, never to satisfy a template. Questions should restore recall or exercise engineering judgment rather than mechanically paraphrase nearby prose; there is no fixed count. References contain only real, verified, useful, topic-specific sources as bare descriptive link bullets with no trailing annotation. Prefer authoritative guides, courses, certifications, standards, implementation sources, playlists, and research papers; omit weak sources, raw image-only links, and repeated pages from the same provider and content type. A materially different resource type may coexist when it independently earns its place. Give broadly useful resources one canonical home per topic family and repeat them only when essential to the specific note; judge arXiv by the same quality and relevance rules as any other source. Examples, mechanism walk-throughs, pitfalls, tradeoffs, comparisons, numbers, diagrams, Questions, References, and other sections are optional explanatory devices chosen for the topic. FolderNotes use the existing card map for direct-child navigation. Do not add standalone `## Links` sections: link vault notes only from prose that explains why the relationship matters, and put external source lists under `# References` when they are useful. Concept pages don't hand-roll sibling navigation because the publish pipeline owns generated "What's next" navigation. For agent examples prefer C# with the Microsoft Agent Framework (`Microsoft.Agents.AI.*`) over Python/Semantic Kernel.

**Interview questions.** Author interview cards once, in the owning note, as collapsed `[!qard]-` callouts. `[!QUESTION]` remains available for generic Question callouts, and both readers accept either key so older or generic content stays readable. The interview template seeds missing `qard-deck` and `qard-topic` from the note's initial path; valid note-level overrides and per-card `qard-location` are user-owned and must survive later moves. Qard's adjacent hidden IDs are protected identity metadata: migration never invents them, and only stock Qard study/edit flows may add or change them. Migration verification may reload and index the live vault, but it never starts a live study event; mutating review/edit checks use a disposable vault. DevBook owns interview-card authoring in current `Vault/Home` notes; stock Qard standalone or AI creation defaults to `Qard/Standalone Deck.md` and needs a separately configured Card Folder before it belongs in this workflow. Native Obsidian preserves its existing disclosure baseline for both Question and Qard: click/touch and FAQ styling match, but titles lack keyboard focus, Enter/Space toggling, `aria-expanded`, and inert collapsed bodies. Quartz supplies those disclosure semantics. This migration documents that accepted host difference and adds no Obsidian accessibility integration.

**Special pages follow their page contract instead of concept-note guidance.** `About.md` keeps its established first-person authorship voice. `index.md` and `Questions.md` are dashboard pages; preserve their Datacore blocks and do not add concept-only headings. `Changelog.md` is generated and must not be hand-edited or reviewed as authorable prose.

**Code fences:** every fence needs a language (MD040); use `text` when nothing fits. Obsidian-specific langs allowed: `mermaid` and `datacorejsx` — Datacore is the vault's one query engine; the legacy Dataview (`dataview`/`dataviewjs`) blocks have been migrated out, so don't add new ones.

**Reviewer gate (mandatory).** After creating or updating any authorable note under `Vault/Home/`, spawn the **note-reviewer** subagent before calling the work done. It is suggest-only (never edits), and completion is blocked until it returns `CLEAN`. It checks repository boundaries, frontmatter and lifecycle, accuracy, the applicable page purposes and headings, the quality of any included Questions or References, MD040, scope-to-depth fit, voice, links, and generated-navigation ownership. Every blocking finding cites concrete evidence; optional polish remains non-blocking, and the absence of an optional explanatory device is not independently a defect. Reviews identify the applicable page type, rules, and protected content for special pages. Concept and FolderNote reviews include a **Split Suggestion**, with splitting based on conceptual separability rather than length. When a task names a prose target, the reviewer handoff includes that target and the available baseline or diff. `CLEAN` counts only when the per-note report gives current-text evidence and a target-resolution verdict; hashes, validators, receipts, and bare verdicts prove integrity, not prose quality.

The recurring DevBook-improvement workflow satisfies this gate with a separate read-only Claude reviewer invocation with built-in web research that receives the current complete note, baseline/diff, sources, rejected proposals, and this reviewer contract. It remains independent from the author invocation and must return the same per-note `CLEAN` evidence. Card membership in an active or saved Qard session is not an exclusion; the workflow may improve card content while leaving plugin state, schedules, review history, settings, and saved sessions untouched.

## Publishing and Quartz

- Edit notes in `Vault/`; never hand-edit generated `Web/content/`. Use the verified Syncer flow in [Web/README.md](Web/README.md) for setup, export and recovery. Keep machine-specific Syncer `data.json` ignored and shared defaults in `.scripts/quartz-syncer.defaults.json`.
- The blocking pre-commit flow stages verified exports with their source changes. Stage intended source first; partial/unstaged source, pre-existing generated changes, failed/skipped exports, timeouts or concurrent source edits block the commit. Never discard source to bypass a failure. Use Syncer's compiled-reference-aware media cleanup; retained media is not verified removal. No background post-commit publication or remote push runs.
- Keep Syncer's Preserve mode so `%%` layout markers survive. Before replacing the bundled temporary build, verify Preserve support against its `build-info.json`. Dashboard and Qard compatibility details belong in the Web README.
- Ground Quartz changes in the [official documentation](https://quartz.jzhao.xyz) with a documentation-specialist/librarian pass before implementation; prefer configuration/plugins over custom code. Authored surfaces are `Web/quartz.config.yaml`, `Web/quartz.ts`, `Web/quartz/styles/custom.scss` and `Web/custom/`. Do not edit other engine files under `Web/quartz/`.
- Follow [DESIGN.md](DESIGN.md) and [StepTrace design guidance](Web/custom/steptrace/DESIGN.md). Node 22 and the Web README own build details. Preserve the committed `quartz.lock.json` baseline; do not commit deployment-time plugin updates automatically. No secrets in site configuration.

The [improvement runbook](docs/devbook-improvement.md) owns scheduled operation, state, quotas and activation. Topic PRs require manual review/merge; credentials and production activation remain separately confirmed. Scheduled candidates prepare dates before independent review; isolated rendering consumes immutable source.
